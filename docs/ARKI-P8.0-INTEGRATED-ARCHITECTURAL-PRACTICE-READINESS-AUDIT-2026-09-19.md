## 4. End-to-end broken bridges

The following bridges are broken or only partial:

```text
PROJECT PURPOSE → CAPABILITY
```

The system can represent purpose and capability, but a general, verified purpose-to-capability selection bridge is not demonstrated for an unseen integrated project.

```text
SYSTEM REQUIREMENT → FUNCTIONAL REQUIREMENT → SPATIAL REALIZATION
```

Requirements, zones, relationships and geometry exist as connected contracts in bounded examples, but a general end-to-end trace for arbitrary integrated projects is not proven.

```text
SPATIAL REALIZATION → CANDIDATE → CANONICAL MODEL
```

The bridge exists for the A21/S1/D6 path, but not as a universally verified architectural synthesis pipeline across all typologies and engineering conditions.

```text
CANONICAL MODEL → MULTIDISCIPLINARY COORDINATION
```

Architecture, structure, MEP, fire and accessibility packages are simulated or reserved. Sized, coordinated and professionally reviewed systems are absent.

```text
EVALUATION → DEFICIT → CAUSE → STRATEGY
```

This bridge is demonstrated for bounded relational cases by D7.6/D7.7. It does not establish general causal diagnosis for all architectural domains.

```text
MUTATION → REEVALUATION → COMPARISON → HUMAN DECISION RECORD
```

The bounded S2 path exists, but complete quality evaluation, engineering impact, regulatory applicability and a project-level human decision record are not universally connected.

```text
OBSERVATION → LEARNING → PERSISTENCE → FRESH RETRIEVAL
```

This is the principal broken bridge. D7.8/D7.8E produced no valid novel learning event; K1 was not created and fresh retrieval/generalization were stopped.

## 7. Safe project input boundary

A clean integrated project may initially supply categories only, without supplying a solution:

| Category | Allowed content |
|---|---|
| Client-provided fact | Users, activities, operational needs, ownership/authority, known constraints |
| Site fact | Survey, parcel boundary, orientation, access, topography, existing conditions, verified location |
| Project objective | Performance, use, cost range, time horizon, social/environmental goals |
| Hard constraint | Site limits, budget ceiling, capacity, required access, non-negotiable program or regulation |
| Preference | Aesthetic, material, organizational or experiential preference, clearly marked as preference |
| Regulatory source | Jurisdiction, applicable RNE/local provisions, source version, professional applicability status |
| Unknown | Missing data explicitly left unresolved |
| Human decision | Accepted intent, rejected alternative, trade-off resolution, confirmation of evidence |

The boundary must exclude a preferred parti, expected zoning, desired geometry, expected deficit, expected cause, preferred alternative and answer key.

## 8. Solution-leakage risks and safe isolation

Current risks include fixed UPAO alternative IDs, titles, geometry endpoints, metric expectations, seeded cost comparisons, Pareto statuses and UI tests that know the intended alternative set.

Safe isolation does not delete history. It should use a separate clean-project namespace, a holdout input package, fixture-free runtime initialization, external test oracle, independent project IDs, withheld expected outputs and a provenance ledger that distinguishes input from derived result. Historical UPAO artifacts should remain available only in a historical/contamination partition.

## 12. Requirements for unseen Project B

Project B must differ structurally, not merely by renaming UPAO-001. It should have a different typology or operational logic, different site/context conditions, different capacity and journey structure, different hard constraints, different regulatory jurisdiction or source applicability, and at least one critically incompatible condition for restraint testing.

Project B must be supplied without a solution, expected pattern, expected deficit, expected cause or preferred alternative. It must be evaluated with the same provenance and human-authority rules, then compared for transfer, adaptation, restraint and fixation independently.

## 13. Recommended next macroorder scope

The next macroorder should be a **controlled integrated practice boundary**, not an autonomous learning or permit-generation macroorder:

1. create a fixture-free project namespace;
2. define the minimum input categories;
3. import only human/site/regulatory evidence;
4. connect purpose → requirements → program → relationships → candidate → canonical model;
5. record every broken bridge and UNKNOWN;
6. require human confirmation before project decisions;
7. keep UPAO-001 as a historical contaminated benchmark;
8. do not create K1 unless a future experiment produces a valid novel observation;
9. run P8.1 only after the clean initialization and traceability gates are explicit.

ARKI has a substantial set of architectural contracts, bounded implementation evidence and a coherent epistemic governance model. # Addendum — P8.1 Controlled Integrated Practice Boundary

## Implemented repair surface

The P8.0 gaps were addressed by extending existing contracts rather than creating a parallel architectural engine. The new module `arkiIntegratedPracticeBoundary.ts` provides the following controlled bridges:

| Repaired bridge | Implemented contract | Honest state |
|---|---|---|
| Clean project initialization | `createCleanProjectBoundary` | Rejects UPAO-001 identifiers and solution-bearing inputs; preserves historical files |
| Purpose → requirements → program → relationships → candidate → canonical model | `buildIntegratedTrace` | Requires every stage, lineage and source reference; missing stages block the trace |
| Canonical model → engineering coordination | `assessCoordination` | Reads the existing multidisciplinary model; unknown calculations remain observations and specialist review is required |
| Regulatory applicability | `assessRegulatoryGate` | Reuses `regulatoryApplicabilityFoundation`; jurisdiction/source/version gaps remain explicit and compliance remains `NOT_ASSESSED` |
| Performance evidence | `assessPerformanceEvidence` | Distinguishes measured, simulated, proxy and unknown evidence; proxy data cannot become compliance |
| Candidate/comparison → human decision | `createIntegratedDecisionTrace` and `recordIntegratedHumanDecision` | DesignMemory receives the decision only through an explicit human-confirmed operation |
| Solution leakage controls | `forbiddenSolutionFields` and negative controls | Preferred parti, zoning, geometry, expected deficit/cause, preferred alternative and answer keys are rejected |
