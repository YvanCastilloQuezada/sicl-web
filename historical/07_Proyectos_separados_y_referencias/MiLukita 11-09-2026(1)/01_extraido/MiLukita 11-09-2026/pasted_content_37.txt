ORDEN 36 — CIERRE DE INFRAESTRUCTURA TERRITORIAL Y PREPARACIÓN DE PRUEBA DE CAMPO

MOTIVO Y PROPÓSITO

El sistema MiLukita Mapper + The Eye ha alcanzado un nivel funcional suficiente en sandbox:

CaptureSession persistente.
WorldObjects versionados.
Claims, Sources y Evidence.
Snapshots históricos inmutables.
Funcionamiento offline.
Sincronización idempotente.
Detección de conflictos.
Resolución manual de conflictos.
Comparación local/remota.
Matriz de evidencia.
Confidence Score explicable.
PublicationStatus separado.
Runtime restringido a la versión publicada.
Auditoría.
RBAC.
Gestor de permisos GPS/cámara.
Historial de sincronización.
Mapa territorial interactivo.

El siguiente objetivo NO es seguir agregando funcionalidades indefinidamente.

El objetivo de esta orden es cerrar la infraestructura necesaria para salir del sandbox y ejecutar la primera prueba real de territorio.

1. REGLA FUNDAMENTAL

NO MODIFICAR MJP CORE.

Mapper, The Eye, World Engine y Runtime deben permanecer desacoplados de MJP CORE.

Ninguna funcionalidad territorial puede alterar:

lógica de juegos;
sorteos;
pagos;
créditos;
resultados;
reglas de MJP CORE.

Si alguna modificación fuese técnicamente inevitable, detenerse y reportarla antes de realizarla.

2. INTEGRACIÓN DE MAPA CARTOGRÁFICO REAL

El mapa actualmente implementado no debe permanecer como simulación para la prueba de campo.

Implementar un Map Provider Adapter, de forma que la aplicación trabaje contra una interfaz cartográfica independiente del proveedor.

Conceptualmente:

Mapper
   ↓
Map Provider Adapter
   ↓
┌───────────────┐
│ Map Provider  │
└───────────────┘

El proveedor concreto podrá ser Google Maps, Mapbox u otro proveedor compatible, pero no acoplar la lógica territorial directamente al proveedor.

Funciones mínimas:
mapa cartográfico real;
zoom;
desplazamiento;
selección de ubicación;
geocodificación;
búsqueda de lugares;
coordenadas;
marcador de WorldObject;
marcador de posición actual;
círculo de precisión GPS;
radio de activación;
visualización de WorldObjects cercanos;
diferenciación visual por estado;
actualización de posición;
manejo de error del proveedor;
manejo de ausencia de conexión.
Importante

Las claves/API credentials deben permanecer fuera del código fuente.

Utilizar configuración mediante variables de entorno/secret management según la arquitectura existente.

No exponer claves privadas en cliente ni en repositorio.

Si el proveedor requiere atribución, respetarla.

3. MODELO CARTOGRÁFICO Y GEOESPACIAL

Verificar que todos los WorldObjects utilicen una representación geoespacial coherente.

Como mínimo:

latitude
longitude
accuracy
altitude (si está disponible)
heading (si está disponible)
timestamp
coordinate_source

Diferenciar:

coordenada capturada por GPS;
coordenada introducida manualmente;
coordenada obtenida por geocodificación;
coordenada corregida posteriormente;
precisión conocida/desconocida.

No tratar todas las coordenadas como igualmente confiables.

La procedencia de la coordenada debe formar parte del expediente territorial.

El Mapper debe mostrar claramente:

● ACTIVO

Si el dispositivo reporta una precisión deficiente, conservar el valor real y advertir al Mapper.

12. PROTECCIÓN DE PUBLICACIÓN

Esta regla es absoluta:

EDITAR WORLDOBJECT
      ≠
MODIFICAR PUBLICACIÓN

La versión publicada debe permanecer congelada e identificable.

Cualquier nueva modificación debe iniciar un nuevo ciclo de revisión si afecta contenido verificable.

No permitir que un Mapper pueda alterar directamente un objeto publicado en Runtime.

16. NO AGREGAR FUNCIONALIDADES POR "PERFECCIONISMO"

Esta orden tiene una condición importante:

No incorporar nuevas funcionalidades que no sean necesarias para el gate de campo.

🔴 BLOCKER — impide la prueba de campo.

🟠 IMPORTANT — debe resolverse antes del lanzamiento público.

🟢 OPTIONAL — puede esperar.

No implementar automáticamente elementos OPTIONAL.

El objetivo es llegar a territorio real, no continuar indefinidamente en sandbox.

Mi evaluación estratégica

Esta orden es mejor que la anterior por una razón: separa claramente software de realidad física.

Hasta ahora hemos estado haciendo algo que puede convertirse en una trampa: cada vez que Manus termina una orden aparecen tres nuevas mejoras y seguimos construyendo. Eso puede durar meses. El sistema ya tiene suficiente estructura para que el próximo aprendizaje importante no venga de otra feature, sino de ponerlo delante de una persona, un teléfono, un GPS, una cámara y un territorio real.

Y hay otra corrección importante respecto a lo que veníamos diciendo:

No diría todavía "sistema 100 % robusto"

Eso es demasiado fuerte.

Lo correcto ahora es:

"La arquitectura y el flujo están suficientemente implementados para pasar al gate de validación física."

Son cosas distintas.

Porque todavía no sabemos, en condiciones reales:

qué tan buena es la precisión GPS;
qué ocurre con mala conectividad;
cuánto pesan realmente las fotografías;
cómo se comporta el almacenamiento local;
cuánto tarda la sincronización;
cómo se comporta la interfaz en una pantalla pequeña;
si los permisos del navegador se comportan como esperamos;
qué pasa cuando el usuario está caminando y capturando;
si el flujo es suficientemente rápido para trabajo de campo.

Y hay una consecuencia importante:

Después de la Orden 36 yo NO haría otra orden grande de backend.

Si Manus devuelve:

"Orden 36 completada. Sugerencias: X, Y, Z..."

las clasificamos. Pero no seguimos automáticamente.

El siguiente movimiento debería ser:

1. Manus → READY FOR FIELD GATE
2. Tú + teléfono A → Mapper
3. Teléfono B → The Eye
4. Salir físicamente a Trujillo
5. Capturar 5–10 objetos
6. Intentar romper el sistema deliberadamente
7. Corregir únicamente los fallos encontrados
8. Recién entonces diseñar la UI definitiva.

Y aquí haría una modificación respecto a nuestro plan anterior: no esperaría a tener la UI "bonita" para hacer el primer levantamiento. Primero necesitamos comprobar que el flujo es usable. Una UI espectacular construida antes de observar el comportamiento real del Mapper puede obligarnos a rediseñarla.

La primera prueba de MiLukita no debería demostrar que "tenemos una aplicación".

Debería demostrar algo mucho más difícil:

que podemos convertir una porción de territorio real en conocimiento digital trazable, verificable y publicable sin perder la cadena de confianza.

Ese es el verdadero producto que estamos construyendo.
