# 1. OBJETIVO GENERAL

La presente Orden Maestra tiene como objetivo **rescatar, consolidar y evolucionar de manera controlada el sistema MiLukita existente**, aprovechando el trabajo ya desarrollado y evitando reconstrucciones innecesarias, duplicaciones, desviaciones de alcance y consumo innecesario de recursos.

El objetivo no es comenzar MiLukita nuevamente.

El objetivo es conseguir que las piezas que ya existen:

* sean identificadas;
* sean comprendidas;
* sean conectadas cuando corresponda;
* sean corregidas cuando sea necesario;
* sean simplificadas cuando exista duplicación;
* sean reemplazadas únicamente cuando exista una justificación técnica;
* y sean presentadas como una experiencia coherente de MiLukita.

La evolución deberá mantener como eje:

**MiLukita → LUKA → Mobile Shell → L★ / Experience / Context → Universal Interaction → Capabilities → módulos especializados.**

---

# 2. PRINCIPIO FUNDAMENTAL

## NO RECONSTRUIR POR DEFECTO.

Antes de crear un componente nuevo deberá determinarse si ya existe:

* un componente equivalente;
* una implementación parcial;
* una implementación desconectada;
* una versión duplicada;
* un servicio reutilizable;
* una capacidad existente;
* una interfaz que pueda ser rescatada.

El orden de actuación será:

**IDENTIFICAR → COMPRENDER → MAPEAR → RESCATAR → INTEGRAR → SIMPLIFICAR → VERIFICAR**

y solo cuando corresponda:

**CREAR LO QUE REALMENTE FALTA.**

---

# 3. VERIFICAR POR DEFECTO; AUDITAR POR EXCEPCIÓN

Esta orden NO autoriza una auditoría general del proyecto en cada fase.

La regla será:

> **VERIFICAR POR DEFECTO; AUDITAR POR EXCEPCIÓN.**

### Verificar

Comprobar específicamente aquello que se haya:

* modificado;
* integrado;
* conectado;
* corregido;
* rescatado;
* reemplazado.

### Auditar

Una auditoría sistemática solo podrá realizarse:

* cuando sea necesaria para resolver un riesgo concreto;
* cuando una inconsistencia impida continuar;
* cuando Human Authority la solicite expresamente.

Descubrir durante una fase que existe otro problema no autoriza automáticamente a resolverlo.

---

# 4. NO EXPANSIÓN DE ALCANCE

El descubrimiento de una oportunidad, problema, mejora o nueva funcionalidad **NO constituye autorización para implementarla**.

Si durante una fase aparece algo que no pertenece al objetivo de dicha fase:

**NO IMPLEMENTAR.**

Cuando sea necesario registrarlo, utilizar:

**OUT_OF_SCOPE / FUERA DE ALCANCE**

y continuar con el objetivo autorizado.

Esto incluye:

* nuevas funcionalidades;
* nuevas experiencias;
* nuevos módulos;
* nuevas integraciones;
* mejoras de UX no relacionadas;
* refactorizaciones generales;
* nuevas capacidades de IA;

* nuevas funciones de AR.

# 10. DISTINCIÓN ENTRE AGENT, SERVICE, ENGINE, ADAPTER, CAPABILITY Y AUTHORITY

No utilizar estos conceptos como sinónimos.

### AGENT

Componente que puede razonar o actuar dentro de capacidades determinadas.

### SERVICE

Servicio funcional del sistema.

### ENGINE

Motor que procesa, calcula, transforma o coordina.

### ADAPTER

Puente entre una capacidad y una superficie, sistema o contexto.

### CAPABILITY

Acción o conjunto de acciones que el sistema permite ejecutar.

### AUTHORITY

Facultad para permitir, rechazar, publicar, aprobar o gobernar.

**Automatización ≠ Autoridad.**

Si durante una fase aparece un problema concreto que requiere una instrucción adicional:

**MICRO-ORDEN**

* alcance;
* prohibiciones;
* criterio de salida.

No utilizar micro-órdenes para convertir una fase en una auditoría general.

# 48. VERIFICACIÓN PROPORCIONAL

No todos los cambios requieren la misma cantidad de pruebas.

### Cambio visual pequeño

Verificación visual/funcional específica.

### Cambio de navegación

Prueba de rutas afectadas.

### Cambio de backend

Pruebas del endpoint/capacidad afectada.

### Cambio de seguridad

Pruebas del control afectado.

### Cambio de datos

Pruebas de persistencia/integridad.

### Cambio transversal

Pruebas específicas de las superficies afectadas.

No ejecutar una batería completa del sistema cuando no sea necesaria para demostrar el cambio.

---

# 49. CRITERIO PARA CREAR COMPONENTES NUEVOS

Un componente nuevo solo deberá crearse cuando:

1. no exista uno reutilizable;
2. las alternativas existentes sean insuficientes;
3. la nueva pieza sea necesaria para el objetivo de la fase;
4. su creación esté justificada;
5. su impacto sea controlado.

No utilizar cuotas artificiales como:

* número mínimo de componentes rescatados;
* porcentaje obligatorio de reducción de duplicación;
* número máximo arbitrario de componentes nuevos.

La calidad de la solución es el criterio.
