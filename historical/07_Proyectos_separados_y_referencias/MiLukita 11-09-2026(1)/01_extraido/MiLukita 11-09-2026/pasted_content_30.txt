0. OBJETIVO

Implementar la primera infraestructura operativa del World Engine de MiLukita, destinada a transformar información del mundo físico en conocimiento territorial estructurado, verificable, versionado y posteriormente publicable en el Runtime de MiLukita.

La arquitectura debe implementar estrictamente:

REALIDAD
   ↓
CAPTURA
   ↓
WORLD OBJECT
   ↓
CLAIMS
   ↓
SOURCES + EVIDENCE
   ↓
THE EYE
   ↓
VERIFICATION
   ↓
HUMAN AUTHORITY
   ↓
PUBLICATION
   ↓
RUNTIME

No confundir captura con verificación ni verificación con publicación.

8. NEARBY INTELLIGENCE

Cuando el Mapper seleccione una ubicación:

mostrar objetos cercanos.

Ejemplo:

Plaza Z          82 m

Si existe una posible duplicación:

⚠ POSIBLE DUPLICADO

Objeto similar encontrado a 7.4 m.

El sistema debe advertir, pero no eliminar automáticamente.

9. VERSIONADO

Cada modificación significativa debe generar una nueva versión.

Nunca sobrescribir silenciosamente una versión previamente verificada.

Ejemplo:

      ↓

      ↓
Modificación
      ↓
WorldObject v2

The Eye debe poder verificar una versión específica.

19. RUNTIME

El Runtime de MiLukita no debe consultar indiscriminadamente los datos de captura.

Debe consumir únicamente entidades y versiones autorizadas.

Regla:

DRAFT              → NO
CAPTURED           → NO
UNDER_REVIEW       → NO
EVIDENCE_REQUIRED  → NO
REJECTED           → NO
ARCHIVED           → NO
OUTDATED           → NO
VERIFIED           → NO automáticamente
PUBLISHED          → SÍ

La condición efectiva de consumo público será:

verification_status = VERIFIED
+
publication_status = PUBLISHED
+
versión autorizada

28. CRITERIO DE ACEPTACIÓN

Manus debe demostrar el siguiente escenario completo:

1. Mapper crea una Capture Session.
2. Mapper se ubica mediante GPS.
3. Captura un objeto real.
4. Sistema registra coordenadas + precisión + fecha.
5. Mapper toma fotografía.
6. Se crea WorldObject.
7. Mapper crea uno o más Claims.
8. Se agregan Sources.
9. Se agregan Evidence.
10. Se guarda versión.
11. Sistema detecta objetos cercanos.
12. Sistema alerta posibles duplicados.
13. Mapper envía a The Eye.
14. The Eye analiza el expediente.
15. The Eye muestra Evidence Matrix.
16. The Eye detecta posibles conflictos.
17. Auditor puede solicitar evidencia.
18. Mapper completa la evidencia.
19. Auditor verifica.
20. Se crea Verification Record.
21. Human Authority autoriza publicación.
22. Se publica una versión específica.
23. Runtime consume únicamente esa versión.
24. Una versión posterior no publicada NO aparece en Runtime.
25. Audit Log registra todo el proceso.

La UI debe ser una representación del sistema, no el sistema mismo.

Y una decisión más: no congelaría todavía el prompt de Gemini

La maqueta que tienes es útil, pero yo no la usaría como especificación visual definitiva.

Primero que Manus implemente la estructura funcional anterior. Después generamos una maqueta de alta fidelidad basada en la interfaz real.

Porque si hacemos al revés, existe un riesgo bastante típico:

Gemini diseña algo espectacular → Manus intenta imitarlo → terminamos optimizando una apariencia que no corresponde al flujo real.

Para MiLukita el orden correcto es:

arquitectura → datos → workflow → funciones → interfaz → estética.

Y esta versión de Mapper + The Eye ya deja planteada una pieza mucho más importante: la infraestructura de confianza del Mundo de MiLukita.

No es necesario agregar más funcionalidades al MVP ahora. Si seguimos agregando cosas, empezamos a construir una plataforma GIS/knowledge graph completa antes de comprobar el producto. Esta orden debe ser el límite funcional de esta fase.
