ORDEN DEFINITIVA PARA MANUS — CIERRE TÉCNICO DE MAPPER + THE EYE

ORDEN: CIERRE TÉCNICO, RESOLUCIÓN DE CONFLICTOS, QA EN DISPOSITIVOS REALES Y PREPARACIÓN PARA UI DEFINITIVA

MOTIVO Y PROPÓSITO

La infraestructura funcional de MiLukita Mapper + The Eye ya cuenta con:

CaptureSession persistente.
Captura y edición de WorldObject.
Versionado.
Snapshots históricos inmutables.
Restauración como nueva versión.
Funcionamiento offline.
Cola de sincronización.
Sincronización idempotente.
Detección de conflictos sin last-write-wins.
Auditoría.
Separación entre captura, verificación y publicación.
Runtime limitado a objetos PUBLISHED.
MJP CORE intacto.

Las pruebas automatizadas actuales también presentan resultados satisfactorios:

TypeScript: PASS.
Build: PASS.
458 pruebas aprobadas.
4 pruebas omitidas.

Sin embargo, pruebas automatizadas no equivalen a validación operacional real.

Mapper será utilizado en campo y, por tanto, debemos demostrar que el sistema funciona correctamente bajo las condiciones reales de uso antes de invertir en la UI definitiva.

Esta orden tiene como objetivo cerrar esa brecha.

1. RESOLUCIÓN VISUAL DE CONFLICTOS

Implementar una interfaz funcional para que The Eye pueda resolver conflictos de sincronización de manera explícita y trazable.

Debe permitir:

Versión A | Versión B

Mostrar lado a lado:

coordenadas;
fecha/hora;
dispositivo;
operador;
versión;
nombre;
tipo;
claims;
sources;
evidence;
fotografías;
modificaciones realizadas.

El auditor debe poder identificar exactamente qué cambió entre ambas versiones.

Decisiones permitidas:
Aceptar A
Aceptar B
Conservar ambas
Solicitar evidencia
Escalar a Human Authority

IMPORTANTE:

La resolución nunca debe eliminar silenciosamente una versión.

La versión descartada debe permanecer disponible en el historial.

Toda resolución debe generar:

usuario;
fecha/hora;
conflicto;
versiones involucradas;
decisión;
justificación;
resultado.

Registrar todo en Audit Log.

2. PROTECCIÓN CONTRA PÉRDIDA DE INFORMACIÓN

Antes de considerar terminada la sincronización offline, verificar explícitamente:

ningún objeto local se pierde;
ninguna fotografía se pierde;
ninguna evidencia se pierde;
ninguna versión histórica se sobrescribe;
una misma operación sincronizada dos veces no genera duplicados;
una desconexión durante sincronización puede recuperarse;
una reconexión posterior continúa correctamente.

Implementar o verificar estados claros:

LOCAL_PENDING

SYNCING

SYNCED

CONFLICT

SYNC_ERROR

El usuario debe poder saber qué ocurrió con cada elemento.

Ejecutar pruebas reales, no solamente simuladas.

Escenario A — Captura online
Abrir Mapper.
Crear CaptureSession.

Guardar.

Escenario B — Captura completamente offline

Desactivar conexión.
Crear sesión.
Capturar varios WorldObjects.
Tomar fotografías.
Registrar GPS.
Registrar notas.

Verificar persistencia.
Recuperar conexión.

Resultado esperado:

Escenario C — Conflicto real

Utilizar dos dispositivos.

Dispositivo A:

modificar WorldObject.

Dispositivo B:

modificar simultáneamente el mismo WorldObject.

Sincronizar ambos.

Verificar que:

no existe last-write-wins;
ambas versiones quedan preservadas;
aparece el conflicto;
The Eye puede resolverlo;
la resolución queda auditada.

7. CODE-SPLITTING

Implementar code-splitting solo si el análisis del build demuestra que existe un problema real de carga inicial.

No realizar optimización por estética técnica.

Medir antes y después:

tamaño inicial;
chunks;
tiempo de carga;
rutas críticas;
carga de Mapper;
carga de The Eye.

Si el beneficio es marginal, documentarlo y no introducir complejidad innecesaria.

10. CRITERIO DE CIERRE

Esta orden solamente se considera completada cuando:

A. Mapper

Puede capturar información real en campo.

B. Offline

Puede trabajar sin conexión y recuperar posteriormente la información.

C. Sync

La sincronización no pierde información ni sobrescribe silenciosamente versiones.

D. Conflicts

Los conflictos pueden visualizarse y resolverse humanamente.

E. The Eye

Puede revisar evidencia y tomar una decisión trazable.

F. Runtime

Solo puede consumir información autorizada para publicación.

G. Audit

Toda transición importante queda registrada.

H. MJP CORE

Permanece intacto y sus pruebas continúan pasando.

El objetivo ahora es cerrar confiabilidad operacional.

Mi evaluación

Esta orden es mejor que la que estabas a punto de enviar.

Hay una diferencia importante: no estamos construyendo Mapper para demostrar que el código funciona; estamos construyendo Mapper para salir físicamente a capturar Trujillo. Esa diferencia cambia qué debemos probar.

Y hay otro punto que corregiría de nuestra línea anterior: la UI de Gemini no debe dictar la arquitectura. Gemini puede servir para diseño visual, pero la interfaz definitiva debe construirse sobre el flujo funcional ya probado. Primero sabemos qué debe hacer el operador; después decidimos cómo se ve.

El orden que recomiendo queda así:

El punto estratégico

No necesitamos seguir acumulando arquitectura indefinidamente.

Después de esta orden, si Manus demuestra el flujo en un teléfono real, tenemos que parar de construir infraestructura y empezar a producir territorio.

Ese será el verdadero test de MiLukita:

¿Podemos tomar un lugar real de Trujillo, documentarlo, demostrar por qué creemos que los datos son ciertos, aprobar una versión y hacer que esa versión aparezca correctamente en el Mundo de MiLukita?

Si la respuesta es sí, dejamos de estar haciendo una plataforma hipotética y empezamos a construir el mundo real de MiLukita.
