ORDEN 34 — CIERRE DE CONFIABILIDAD OPERACIONAL DE MILUKITA MAPPER + THE EYE

ORDEN PARA MANUS: QA EN CAMPO + COMPARACIÓN VISUAL DE VERSIONES + RATE LIMITING TERRITORIAL + CERTIFICACIÓN DE CIERRE

0. PROPÓSITO DE LA ORDEN

La infraestructura de MiLukita Mapper + The Eye ya dispone de captura territorial, sesiones, WorldObjects, versionado, snapshots, funcionamiento offline, sincronización idempotente, detección de conflictos, resolución manual, auditoría y separación de publicationStatus.

La Orden 34 tiene un propósito específico:

demostrar que esta infraestructura funciona correctamente en condiciones reales de operación y dejarla lista para recibir la UI definitiva.

No se busca agregar nuevas funcionalidades de producto.

No se busca ampliar el World Engine.

No se busca modificar MJP CORE.

Se busca cerrar técnicamente el ciclo de captura → sincronización → conflicto → verificación → autorización → publicación.

2. QA CON DATOS REALES EN DISPOSITIVOS REALES

Realizar una prueba operacional utilizando dispositivos físicos y datos territoriales reales.

Preferentemente utilizar un entorno de staging/QA, evitando contaminar el Runtime público.

Prueba 2.1 — Captura online

El Mapper deberá:

Iniciar una CaptureSession.
Obtener posición GPS.
Registrar precisión GPS.
Capturar fotografía.
Crear un WorldObject.
Registrar una nota.
Asociar evidencia.
Guardar.
Editar el objeto.
Generar una nueva versión.
Enviar a The Eye.

Verificar que toda la información llegue correctamente.

Prueba 2.2 — Captura offline

Con el dispositivo sin conexión:

Crear una sesión.
Crear varios WorldObjects.
Capturar fotografías.
Registrar GPS.
Registrar notas.
Editar objetos.
Cerrar la aplicación.
Volver a abrirla.
Confirmar que la información continúa disponible.
Recuperar conexión.
Ejecutar sincronización.

Verificar:

ningún objeto perdido;
ninguna fotografía perdida;
ninguna evidencia perdida;
ninguna versión sobrescrita;
ninguna operación duplicada.

5. RESOLUCIÓN DEL CONFLICTO

Desde la comparación de versiones, The Eye/Human Authority podrá:

Mantener A
Mantener B
Combinar
Marcar como DISPUTED
Solicitar evidencia

La operación Combinar debe generar una nueva versión, no modificar retroactivamente las versiones originales.

Las versiones originales deben permanecer intactas.

Toda resolución debe registrar:

responsable;
fecha/hora;
versiones utilizadas;
decisión;
justificación;
nueva versión resultante, cuando corresponda.
6. RATE LIMITING TERRITORIAL

Implementar protección específica para endpoints territoriales.

No utilizar un único límite global arbitrario.

Definir límites configurables por:

endpoint;
método;
usuario/rol;
IP cuando corresponda;
tipo de operación.

Diferenciar al menos:

Lectura

Consultas de WorldObjects y sesiones.

Escritura

Creación y modificación.

Operaciones pesadas
uploads;
fotografías;
evidencia;
importaciones masivas;
sincronización.

Los límites deben estar centralizados en configuración y no dispersos en el código.

Verificar que un usuario que exceda el límite reciba una respuesta controlada y registrada.

7. SEGURIDAD DE RATE LIMITING

Verificar que el rate limiting:

no pueda ser evadido simplemente cambiando parámetros del cliente;
sea aplicado server-side;
no dependa exclusivamente de la interfaz;
registre eventos relevantes;
no bloquee injustificadamente a operadores legítimos.
8. PRUEBA DE INTEGRIDAD DE PUBLICACIÓN

Ejecutar pruebas intentando modificar un objeto que ya tenga una versión publicada.

Debe cumplirse:

VERSION PUBLICADA
      ↓
NUEVA EDICIÓN
      ↓
NUEVA VERSIÓN
      ↓
PUBLICATION STATUS NO CAMBIA AUTOMÁTICAMENTE

La nueva edición no debe reemplazar silenciosamente la versión publicada.

Solo una autorización explícita debe modificar qué versión consume Runtime.

9. PRUEBA NEGATIVA DEL RUNTIME

Intentar introducir en Runtime objetos/versions:

DRAFT
CAPTURED
UNDER_REVIEW
EVIDENCE_REQUIRED
DISPUTED
REJECTED
ARCHIVED

Todos deben quedar fuera del Runtime.

Probar también que una versión nueva, aunque esté correctamente creada, no sustituye automáticamente una versión publicada.

15. CRITERIO DE CIERRE

La orden se considera completada cuando Manus pueda afirmar, con evidencia:

1. Mapper funciona en dispositivo real.

2. Mapper funciona offline.

3. La sincronización no pierde información.

4. Los conflictos no se resuelven automáticamente de forma destructiva.

5. The Eye puede comparar versiones.

6. The Eye puede resolver conflictos.

7. Las decisiones quedan auditadas.

8. Una edición nunca sustituye silenciosamente una publicación existente.

9. Runtime solo consume versiones autorizadas.

10. Los endpoints territoriales tienen protección server-side.

11. MJP CORE permanece intacto.
