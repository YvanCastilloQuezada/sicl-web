1. Objetivo del contrato
Definir el modelo arquitectónico semántico 3D de ARKI, tal que:

Cada elemento (muro, losa, columna, puerta, etc.) sea un ente vivo con identidad estable.

Su mutación (mover, redimensionar, eliminar) se propague por la cadena H-001 → H-005.

Su representación (2D, 3D, IFC) sea múltiple, coherente, y generada desde el mismo estado.

Su verificación pase por A-002 antes de afirmar que un cambio es válido.

Su exportación a IFC sea real (IfcOpenShell 0.8.5), no simulada.

Falle cerrado donde falta motor (OCC, Blender): no finge lo que no tiene.

Un solo estado arquitectónico. Múltiples representaciones. Cero alucinaciones.

3. Modelo semántico — ArchiElement
3.1 Identidad
python
@dataclass(frozen=True)
class ArchiElementId:
    """Identidad determinista y estable de un elemento arquitectónico."""
    value: str          # sha256 hex de (project_id, kind, canonical_geometry, birth_version)
    
    def __post_init__(self):
        if len(self.value) != 64 or any(c not in "0123456789abcdef" for c in self.value):
            raise ValueError("ArchiElementId must be 64 hex characters")
python
@dataclass(frozen=True)
class IfcGlobalId:
    """IFC GlobalId gobernado (22-char base64 IFC)."""
    value: str
    
    def __post_init__(self):
        if len(self.value) != 22:
            raise ValueError("IfcGlobalId must be 22 characters (IFC spec)")
Reglas:

ArchiElementId se computa determinísticamente desde el proyecto + tipo + geometría canónica + versión de creación.

Sin Math.random, sin Date.now, sin UUIDs no reproducibles.

IfcGlobalId se genera con el algoritmo IFC (sha256 → base64 → 22 chars) y es reproducible desde el ArchiElementId + proyecto.

3.3 Estructura del elemento
python
@dataclass(frozen=True)
class ArchiElement:
    element_id: ArchiElementId
    kind: ElementKind                    # WALL | SLAB | COLUMN | ...
    project_id: str
    name: str
    geometry: ArchiGeometry              # ver §4
    hosting: tuple[ArchiElementId, ...]  # quién lo aloja (para Door/Window/Opening)
    contained_in: ArchiElementId | None  # quién lo contiene (para Space)
    properties: tuple[tuple[str, str], ...]  # pares clave-valor ordenados
    version: int
    provenance: tuple[str, ...]          # evidence ids de A-002 u otro
Reglas duras:

properties es una tupla ordenada de pares. Determinista. Sin dict (el orden no es estable).

hosting y contained_in son referencias a otros ArchiElementId.

Un elemento no puede alojar y contener a la vez (validación en __post_init__).

3.4 Relaciones entre elementos
python
@dataclass(frozen=True)
class ArchiRelationship:
    kind: RelationshipKind               # HOSTED_IN | CONTAINS | ADJACENT_TO | BOUNDS
    source: ArchiElementId
    target: ArchiElementId
    provenance: tuple[str, ...]
Relaciones v1:

HOSTED_IN: Door/Window/Opening → Wall/Slab.

CONTAINS: Space → Wall/Slab que lo delimitan.

BOUNDS: Wall → Space (muro delimita espacio).

Sin ADJACENT_TO en v1. Va a v2. Solo si el PoC lo demuestra necesario.

4. Geometría — vía IfcOpenShell 0.8.5
4.1 Estrategia
No hay OCC. Eso significa:

No BRep real.

No operaciones booleanas complejas.

Sí extrusión paramétrica vía IfcOpenShell.

Sí perfiles IFC estándar (rectangular, circular).

4.2 Contrato de geometría
python
@dataclass(frozen=True)
class ArchiGeometry:
    kind: GeometryKind                   # EXTRUDED_RECTANGLE | EXTRUDED_CIRCLE
    origin: tuple[float, float, float]   # mm en world coordinates
    direction: tuple[float, float, float]  # vector unitario de extrusión
    profile: ProfileSpec                 # rectangular o circular
    length: float                        # mm
    material_ref: str | None
Reglas:

Todas las unidades en milímetros (consistente con A-002 y ARKI-DRAW).

origin y direction son tuplas de 3 floats.

Sin Matrix4, sin Transform opacos. Solo lo que se puede serializar determinísticamente.

4.3 Representación IFC

Sin inventar tipos IFC. Si un tipo no está en la lista, no se exporta en v1.

5. Mutación semántica — el "ente vivo"
Regla central: mover un muro no es mover un polígono. Es una operación arquitectónica que dispara la cadena cognitiva.

5.1 Contrato de mutación
python
@dataclass(frozen=True)
class ArchiMutation:
    kind: MutationKind                   # MOVE | RESIZE | ADD_OPENING | DELETE
    target: ArchiElementId
    payload: tuple[tuple[str, str], ...] # parámetros ordenados
    requested_by: str                    # actor id
    requested_at_iso: str                # no auto-generado
5.2 Cadena obligatoria
Cualquier mutación sigue este flujo sin excepción:

text
1. Validar que el target existe en el proyecto.
2. Verificar con A-002 si hay información suficiente para afirmar la mutación.
   → Si A-002 dice BLOCK, la mutación no procede.
3. Registrar en H-001 el cambio como nueva derivación (DerivationRecord).
4. Consultar H-002: ¿qué elementos se afectan?
   → Si H-002 no encuentra impactos, se declara UNKNOWN, no "todo bien".
5. Consultar H-003: ¿sigue siendo válido el estado tras la mutación?
6. Consultar H-004: ¿qué acciones planificar (RECOMPUTE, REVIEW, ESCALATE)?
7. Solo acciones con `requires_human_authority=False` se ejecutan automáticamente.
8. H-005 ejecuta recomputación selectiva si corresponde.
9. Se regenera la representación 2D/3D/IFC de los elementos afectados.
10. Se emite reporte completo con provenance de cada paso.
Esta cadena no es opcional. Es el contrato.

5.3 Regla de propagación
Si un elemento cambia, todo lo que depende de él cambia. Áreas, metrados, costos, representación, IFC, render (cuando exista).

Se implementa usando la cadena H-001→H-005 existente, no reinventando la propagación.

6. Integración con el Core cognitivo
6.1 Con H-001
Cada ArchiElement creado o mutado genera un DerivationRecord:

text
output:     VersionedRef("Wall", "W-14", version, content_hash)
inputs:     (todos los elementos de los que depende)
method:     "archi.create" | "archi.move" | "archi.resize" | ...
method_version: "1"
6.2 Con H-002
ArchiMutation debe poder convertirse en un ImpactChange para consultar impactos.

6.3 Con H-003
El ArchiElement afectado debe poder evaluarse con ValidityAnalyzer.

6.4 Con H-004
El ReactionPlan producido por H-004 se ejecuta sobre los elementos afectados.

6.5 Con H-005
SelectiveRecomputationEngine recomputa solo lo que H-002 marcó como afectado.

6.6 Con A-002
ArchiMutation requiere un SufficiencyRequest con operation="preliminary building massing" (u otra). El gate A-002 → H-005 ya existe y se reutiliza.

Nada de esto se reinventa. Se reutiliza la cadena.
