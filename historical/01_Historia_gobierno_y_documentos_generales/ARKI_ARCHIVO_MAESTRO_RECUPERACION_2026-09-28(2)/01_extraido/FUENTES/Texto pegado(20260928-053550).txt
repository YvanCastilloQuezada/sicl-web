1. Decisión previa sobre RT-D2.1-02 (atomicidad)
Consulta al Core congelado: ¿se puede resolver sin modificar H-001?

Análisis:

DerivationLedger.record() es un método público de H-001.

SQLiteRepository.transaction() existe pero no se usa desde el ledger.

Modificar DerivationLedger para aceptar un contexto transaccional cambia H-001. Prohibido.

Conclusión: no se modifica H-001. La atomicidad se resuelve desde dentro de ArchiTransaction con rollback explícito en caso de fallo parcial.

Estrategia concreta:

En transaction.py::apply_full_chain, antes de publicar:

Recolectar los records a publicar en una lista to_publish.

Registrar cada uno, capturando (project_id, record_id) en published_ids.

Si cualquier ledger.record() falla:

No hay rollback disponible en H-001 — pero podemos declarar BLOCKED_BY_CORE_CONTRACT para la garantía estricta "all-or-zero".

Alternativa viable: verificar antes de publicar que los IDs no colisionan y que el ledger está en estado limpio (no hubo cambios desde que se construyó temp). Esto no elimina el riesgo de fallo a mitad, pero lo reduce al mínimo.

Decisión operativa: implementar el fix como pre-verificación + publicación secuencial con abort en el primer fallo y declaración explícita del gap:

python
records_to_publish = [
    r for r in temp.list(mutation.project_id)
    if r.id not in {x.id for x in ledger.list(mutation.project_id)}
]

# Pre-verificación: IDs únicos, no colisionan entre sí.
seen = set()
for r in records_to_publish:
    if r.id in seen:
        return MutationResult(..., status=FAILED, reason="PUBLISH_DUPLICATE_ID_IN_BATCH")
    seen.add(r.id)

# Publicación secuencial.
published = []
try:
    for r in records_to_publish:
        ledger.record(mutation.project_id, r, actor="ARCHI_D2")
        published.append(r.id)
except Exception as exc:
    # H-001 no ofrece rollback atómico.
    # Declarar gap explícitamente.
    return MutationResult(
        mid, MutationStatus.FAILED, MutationLifecycle.EVALUATED,
        self._canonical, (),
        f"PARTIAL_PUBLISH:{len(published)}_of_{len(records_to_publish)}:{type(exc).__name__}",
        False, {**prov, "partial_publish": published}
    )
Y declarar en prov:

python
prov["atomicity"] = {
    "all_or_zero": False,
    "reason": "DERIVATION_LEDGER_HAS_NO_BATCH_COMMIT_AT_API_BOUNDARY",
    "partial_failure_detected": False,
}
Esto no cierra el finding como "atomicidad garantizada", pero:

Detecta y reporta publicación parcial si ocurre.

Declara explícitamente el límite del Core congelado.

No finge una garantía que no existe.

Si el PO considera esto insuficiente, la alternativa es BLOCKED_BY_CORE_CONTRACT. Mi recomendación: aceptar el fix con gap declarado y registrar como KNOWN_LIMITATION en el contrato D-1.
