ORDEN DE GENERACIÓN DE CÓDIGO — L★ / QR
MODO: BACKEND / LÓGICA / DATOS / API / TESTS

OBJETIVO

Aprovechar el entorno actual de Manus exclusivamente para generar,
completar o reforzar CÓDIGO FUNCIONAL de MiLukita relacionado con
L★ / QR.

ESTA ORDEN NO AUTORIZA TRABAJO DE FRONTEND.

============================================================
1. PROHIBICIÓN ABSOLUTA DE FRONTEND
============================================================

NO modificar:

- JSX
- TSX de interfaces
- CSS
- estilos
- Tailwind
- diseño visual
- layouts
- componentes visuales
- iconos
- animaciones
- responsive design
- colores
- tipografías
- navegación visual
- landing pages
- dashboards visuales
- botones
- menús
- modales
- páginas existentes.

NO reconstruir ninguna interfaz.

NO hacer "mejoras visuales".

NO corregir problemas estéticos.

NO crear nuevas pantallas.

NO convertir una funcionalidad en una nueva página.

Si una funcionalidad necesita frontend para ser utilizada,
NO implementarla visualmente.

Implementar solamente la lógica, API, servicios, tipos,
persistencia y tests que permitan que el frontend existente
pueda utilizarla posteriormente.

============================================================
2. INSPECCIÓN PREVIA
============================================================

Primero localizar en el código existente:

- L★
- QR
- QR Generator
- QR Studio
- Circular QR
- MiLukitaCircularQR
- customQrGenerator
- circularQr
- rutas/API relacionadas
- servicios relacionados
- modelos de datos relacionados.

Determinar qué lógica ya existe.

NO duplicar funcionalidades existentes.

NO crear una segunda arquitectura paralela.

============================================================
3. ACTIVE SHARE TARGET
============================================================

Implementar exclusivamente la lógica necesaria para resolver:

resolveActiveShareTarget()

Debe devolver un objeto de dominio claramente tipado.

Prioridad:

1. ACTIVE EXPERIENCE
2. AUTHORIZED SESSION
3. PUBLIC LUKA

Ejemplo conceptual:

{
  type: "EXPERIENCE" | "SESSION" | "PUBLIC_LUKA",
  targetId: string | null,
  url: string,
  expiresAt: string | null
}

Adaptar al modelo real del proyecto.

NO crear interfaz para esto.

============================================================
4. SERVICIO DE RESOLUCIÓN
============================================================

Crear o completar un servicio de dominio/backend para:

- resolver destino QR
- validar contexto
- validar existencia
- validar expiración
- validar revocación
- determinar tipo de QR
- generar URL segura.

Separar:

QR RESOLUTION

de

AUTHORIZATION.

============================================================
5. QR PÚBLICO
============================================================

Implementar la generación/resolución del destino público de LUKA.

El QR público NO debe contener:

- credenciales
- sesiones administrativas
- tokens de autorización
- secretos
- información privada.

============================================================
6. QR DE EXPERIENCIA
============================================================

Implementar la lógica necesaria para representar una experiencia
específica.

Debe existir una identificación inequívoca del target.

Validar:

- existencia
- estado
- disponibilidad
- publicación cuando corresponda.

No permitir que un QR público acceda directamente a recursos
privados.

============================================================
7. QR DE SESIÓN
============================================================

Implementar exclusivamente backend/lógica para:

- creación de token opaco
- expiración
- revocación
- validación
- resolución del target
- invalidación.

El token NO debe contener permisos administrativos.

IMPORTANTE:

ESCANEAR QR NO CONCEDE AUTORIZACIÓN.

La autorización debe continuar dependiendo de:

AUTHENTICATION
+
RBAC
+
CAPABILITY CHECK.

============================================================
8. SHARE TARGET
============================================================

Crear o completar un modelo de dominio para representar:

PUBLIC_LUKA
EXPERIENCE
SESSION

Evitar lógica dispersa en componentes frontend.

La resolución debe estar centralizada.

============================================================
9. SHARE SERVICE
============================================================

Crear o completar un servicio equivalente conceptualmente a:

ShareService

con funciones como:

- resolveActiveShareTarget()
- createExperienceShare()
- createSessionShare()
- revokeSessionShare()
- resolveShareToken()
- validateShareTarget()
- getPublicLukaTarget()

Usar los nombres y arquitectura existentes cuando corresponda.

NO duplicar servicios si ya existen.

- RBAC
- capability
- expiración
- revocación.
