1. Qué aprendimos hoy

El descubrimiento principal es que una inteligencia arquitectónica no debe aprender edificios como colecciones de habitaciones.

Debe aprenderlos como sistemas de actividades humanas, procesos, relaciones, flujos, controles, interfaces, condiciones y necesidades que posteriormente pueden adquirir una realización espacial.

La transformación conceptual fundamental fue:

Éste es probablemente el aprendizaje más importante de toda la investigación de hoy.

2. La primera enseñanza para ARQUI
ARQUI no debe comenzar preguntando “¿qué habitaciones necesita?”

Debe comenzar preguntando:

¿Qué tiene que poder ocurrir aquí para que este proyecto cumpla coherentemente su propósito?

Ese cambio parece pequeño, pero modifica completamente la inteligencia del sistema.

Una vivienda no empieza con:

SALA
COMEDOR
COCINA
DORMITORIO
BAÑO

Empieza con:

HABITAR
↓
descansar
alimentarse
cuidarse
relacionarse
tener privacidad
guardar
trabajar/estudiar si corresponde
mantener
limpiar
recibir
entrar/salir

Sólo después ARQUI estudia cómo espacializar esas necesidades.

3. La enseñanza más fuerte: mínimo sistema ≠ mínimo ambiente

Llegamos a una corrección fundamental:

MINIMUM SYSTEM ≠ MINIMUM ROOM

Un edificio puede necesitar una función esencial sin necesitar necesariamente un recinto independiente para ella.

Por ejemplo:

STORAGE REQUIRED

no implica:

STORAGE ROOM REQUIRED

Puede resolverse mediante:

closet
cabinet
wall system
furniture
distributed storage
dedicated room
external facility
shared facility

dependiendo del proyecto.

Por eso ARQUI debe pensar:

SYSTEM REQUIREMENT
    ↓
POSSIBLE REALIZATIONS

y no:

SYSTEM REQUIREMENT
    ↓
ROOM
4. Qué significa realmente “mínimo”

También aprendimos que estábamos mezclando dos conceptos.

Debe separarse:

SYSTEM ROLE

de:

FUNCTIONAL NECESSITY

Un sistema puede desempeñar un papel:

PRIMARY
SUPPORT
CONTROL
SERVICE
INFRASTRUCTURE
INTERFACE

pero su necesidad puede ser:

ESSENTIAL
CONDITIONAL
OPTIONAL
NOT_APPLICABLE
UNKNOWN

Esto produce una regla especialmente importante:

SUPPORT SYSTEM ≠ OPTIONAL SYSTEM

Un sistema de apoyo puede ser absolutamente esencial para que el edificio funcione.

5. Funcionalmente esencial tampoco significa legalmente obligatorio

Otra distinción importante:

FUNCTIONALLY ESSENTIAL
≠
LEGALLY MANDATORY

y:

LEGALLY MANDATORY
≠
TYPOLOGICALLY ESSENTIAL

ARQUI debe conservar ambas fuentes de obligación.

Conceptualmente:

FUNCTIONAL KNOWLEDGE
        +
APPLICABLE REGULATION
        +
PROJECT REQUIREMENTS
        +
VERIFIED TECHNICAL REQUIREMENTS
        ↓
PROJECT OBLIGATIONS

Nunca debe convertir automáticamente conocimiento tipológico en norma.

6. Qué aprendimos sobre tipologías

Una tipología arquitectónica no debería definirse por su lista habitual de habitaciones.

Una definición más potente es:

Una tipología es una organización funcional arquitectónica recurrente caracterizada por determinados propósitos, actores, sistemas, procesos, relaciones y patrones operativos.

Por tanto:

TYPOLOGY
+
FUNCTIONAL PROFILE
+
PROJECT CONTEXT
→
SYSTEM REQUIREMENTS

Esto permite que dos hospitales, colegios, hoteles o viviendas de la misma familia sean realmente diferentes.

No basta enseñar:

Porque el motivo permite transferir el conocimiento.

Si cambia el proyecto, ARQUI puede volver a razonar la relación.

11. Organigrama no es conocimiento canónico independiente

Aprendimos que el organigrama debería ser una vista del conocimiento.

Conceptualmente:

KNOWLEDGE GRAPH
        ↓
FUNCTIONAL VIEW

FLOW VIEW
CONTROL VIEW
INTERFACE VIEW

Por tanto:

ORGANIGRAM IS A VIEW OF FUNCTIONAL KNOWLEDGE, NOT THE KNOWLEDGE ITSELF.

Esto permitirá generar diferentes diagramas desde una misma verdad semántica.

12. Flujo, proceso y circulación tampoco son lo mismo

Debe quedar profundamente aprendido:

PROCESS
=
qué sucede y en qué secuencia

FLOW
=
quién o qué se desplaza

CIRCULATION
=
qué red espacial permite ese movimiento

Entonces:

PROCESS ≠ FLOW ≠ CIRCULATION

y:

FLOW ≠ CORRIDOR

13. Los estados son fundamentales

La investigación mostró que la arquitectura cambia funcionalmente aunque la geometría permanezca igual.

Ejemplo hotel:

AVAILABLE
→ OCCUPIED
→ DIRTY
→ CLEANING
→ INSPECTED
→ AVAILABLE

Industria:

RAW
→ IN PROCESS
→ FINISHED

Logística:

RECEIVED
→ STORED
→ PICKED
→ STAGED
→ SHIPPED

Edificio:

NORMAL
EVENT
EMERGENCY
MAINTENANCE

Por eso:

PHYSICAL TOPOLOGY ≠ OPERATIONAL TOPOLOGY

Ésta es una enseñanza muy potente para ARQUI.

15. Capacidad tampoco es una sola cifra

ARQUI no debería recibir:

Puede tratarse de:

Por tanto:

CAPACITY ≠ SPACE COUNT

POPULATION ≠ THROUGHPUT

18. Completitud funcional

También aprendimos:

SYSTEM PRESENT ≠ SYSTEM RESOLVED

Un sistema puede aparecer nominalmente y continuar mal resuelto.

Por eso ARQUI debe poder preguntar:

¿están definidos los actores?

¿actividades?

¿recursos?

¿proceso?

¿flujos?

¿relaciones?

¿controles?

19. Esto permite descubrir déficits reales

Un déficit funcional no debe ser:

“No encuentro una habitación llamada X.”

Debe ser:

“Existe una necesidad funcional esencial que todavía no tiene una resolución demostrable.”

Eso cambia radicalmente la crítica arquitectónica.

20. También aprendimos a distinguir vacío geométrico y vacío funcional

EMPTY GEOMETRY ≠ FUNCTIONAL VOID

Puede existir:

empty space

que sea deliberado y arquitectónicamente válido.

Y puede existir un edificio aparentemente completamente ocupado geométricamente que tenga:

functional deficit

grave.

ARQUI debe poder distinguirlos.

27. El gran límite profesional

ARKI puede saber:

a span exists
a load path is needed
a shaft is required
a technical route must exist
maintenance access is necessary

sin afirmar:

beam = 30×60 cm
duct = 450 mm
pipe = 100 mm

si no existe cálculo o fuente competente.

De ahí:

GEOMETRICALLY POSSIBLE ≠ TECHNICALLY FEASIBLE

45. La precisión debe crecer junto con la evidencia

Una regla que resume gran parte de todo el trabajo:

DESIGN RESOLUTION SHALL NOT OUTRUN EVIDENCE RESOLUTION.

Y también:

GEOMETRIC PRECISION MUST NOT EXCEED KNOWLEDGE PRECISION.

Esto evita que ARQUI produzca falsos detalles simplemente porque puede dibujarlos.

46. Qué enseñanza me dejó a mí esta investigación

La principal es que el reto de una IA arquitectónica no está en generar más geometría.

Está en mantener una cadena de razonamiento coherente desde:

WHY?

hasta:

WHAT?

y finalmente:

HOW COULD IT BE REALIZED?

sin confundir esas tres preguntas.

Una IA puede generar miles de plantas.

Eso no significa que comprenda arquitectura.

48. Tercera enseñanza

Una buena ontología arquitectónica no debe describir todos los edificios posibles. Debe permitir describirlos.

Es una diferencia fundamental.

No necesitamos codificar todas las soluciones.

Necesitamos una gramática suficientemente poderosa para representarlas y razonarlas.

53. ARQUI debe aprender a preguntar antes de diseñar

Cuando falten datos críticos debería preguntar, por ejemplo:

Who are the users?

Simultaneously or per day?

What operating hours?

What activities occur?

What equipment is involved?

What must remain separated?

What can be shared?

What can change over time?

What external systems are required?

What site data are known?

No generar inmediatamente una planta plausible.

“La geometría funciona, pero el sistema de suministro no está resuelto.”

o:

“El programa parece completo por nombres, pero falta una interfaz funcional entre recepción y procesamiento.”

Eso sería crítica arquitectónica real.

55. Cómo se puede ampliar

Aquí está la parte más importante hacia adelante.

La arquitectura descubierta hoy permite crecer en varias direcciones sin cambiar el núcleo.

La expansión debería ocurrir agregando:

MORE KNOWLEDGE
+
MORE METHODS
+
MORE EVIDENCE
+
MORE TYPOLOGIES
+
MORE REGULATORY CORPORA
+
MORE TESTS

no agregando una nueva arquitectura cada vez.

56. Ampliación tipológica

Podemos profundizar cada familia:

TYPOLOGY
↓
SUBTYPES
↓
FUNCTIONAL PROFILES
↓
SYSTEM REQUIREMENTS
↓
PROCESSES
↓
VARIANTS

Ejemplo:

EDUCATION
├── early childhood
├── primary
├── secondary
├── technical
├── university
├── laboratory-intensive
└── specialized

sin crear siete motores.

57. Ampliación multiescala

El mismo razonamiento puede extenderse hacia:

ROOM
BUILDING
CAMPUS
BLOCK
NEIGHBORHOOD
CITY
REGION
COUNTRY

pero agregando métodos propios de cada escala.

Por ejemplo:

BUILDING
→ circulation graph

CITY
→ mobility/access network

Puede existir matemática similar, pero:

SAME MATHEMATICS ≠ SAME ARCHITECTURAL MEANING.

RNE

↓
LOCAL / MUNICIPAL

ENVIRONMENTAL

manteniendo siempre:

jurisdiction

applicability

coverage

Más adelante:

PERU
COLOMBIA

USA

...

sin mezclar reglas.

La arquitectura regulatoria debe permitir:

PROJECT
→ JURISDICTION
→ APPLICABLE CORPUS

y nunca asumir que una regla extranjera aplica localmente.

una misma verdad del proyecto

y no crear versiones incompatibles del edificio.

PRECEDENT ≠ TEMPLATE

Pero:

OBSERVED PRACTICE ≠ REGULATION

y tampoco:

OBSERVED PRACTICE ≠ AUTOMATIC BEST PRACTICE

63. Ampliación mediante aprendizaje humano

Las correcciones del arquitecto podrían convertirse en:

CORRECTION
↓
RATIONALE
↓

↓
CANDIDATE KNOWLEDGE
↓
REPEATED EVIDENCE
↓
TRANSFER TEST
↓
POSSIBLE LEARNED PRINCIPLE

Nunca:

one correction
→ universal rule
64. La meta que emerge

Si aplicamos correctamente todo esto, ARQUI dejaría de ser principalmente:

“una IA que genera arquitectura”

para convertirse progresivamente en:

una inteligencia arquitectónica que formula problemas, estructura conocimiento, genera alternativas, explica decisiones, detecta ausencias y contradicciones, reconoce límites, aprende principios, los transfiere entre contextos y trabaja con el arquitecto sin sustituir su autoridad.

Ésa es una meta bastante más exigente.

Y también bastante más valiosa.

66. Qué no debe perderse al implementarlo

Toda ampliación futura debería poder responder:

WHAT DO WE KNOW?

WHY DO WE BELIEVE IT?

WHERE DID IT COME FROM?

WHEN DOES IT APPLY?

WHEN DOES IT NOT APPLY?

WHAT IS STILL UNKNOWN?

WHAT DEPENDS ON IT?

WHAT ALTERNATIVES EXIST?

WHAT HAS BEEN VERIFIED?

WHAT REQUIRES A SPECIALIST?

WHAT REQUIRES HUMAN JUDGMENT?

Si ARQUI mantiene esas preguntas, puede crecer muchísimo sin volverse una caja negra.

67. Cierre del handoff

La enseñanza central de esta jornada puede resumirse en una sola transformación:

DO NOT TEACH ARQUI
WHAT BUILDINGS LOOK LIKE.

TEACH ARQUI
WHY BUILDINGS NEED WHAT THEY NEED,
HOW THOSE NEEDS RELATE,
HOW THEY CAN BE SPATIALLY REALIZED,
HOW CONTEXT CHANGES THEM,
HOW TO VERIFY THEM,
AND WHEN ARQUI DOES NOT KNOW ENOUGH.

Y de ahí deriva la regla final:

ARQUI debe aprender arquitectura como un sistema de razonamiento transferible, trazable y ampliable; las formas, programas, organigramas y planos son consecuencias posibles de ese conocimiento, no el conocimiento mismo.
