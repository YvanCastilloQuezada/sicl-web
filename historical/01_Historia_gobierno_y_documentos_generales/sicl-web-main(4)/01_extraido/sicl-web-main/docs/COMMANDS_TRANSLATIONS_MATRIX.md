## Recomendación de diseño

La mejor opción es un **modelo híbrido**:

1. El selector de idioma cambia la interfaz, las etiquetas, las descripciones, los argumentos y las sugerencias.
2. El usuario puede escribir o seleccionar el alias localizado.
3. Antes de ejecutar, el frontend transforma el alias localizado al comando canónico SICL.
4. El Core recibe únicamente la forma canónica para conservar compatibilidad, auditoría y validación.
5. La interfaz muestra una confirmación bilingüe opcional: alias localizado → comando canónico.
6. El historial conserva ambos valores: `display_command` y `canonical_command`.

## Ejemplo

Con idioma español seleccionado:

```text
/PROYECTO CREAR P-001 Vivienda
```

El frontend normaliza y envía al Core:

```text
/PROJECT CREATE P-001 Vivienda
```

## Riesgos que deben evitarse

- No traducir silenciosamente el comando antes de mostrarlo al usuario.
- No enviar alias localizados directamente al Core sin un contrato aprobado.
- No traducir identificadores, valores JSON, fechas, unidades, estados técnicos ni nombres de entidades sin reglas explícitas.
- No permitir que dos alias ambiguos se resuelvan al mismo comando sin mostrar la desambiguación.

## Próximo RFC recomendado

**RFC-019 — Localized SICL Command Aliases.** Debería definir el registro de alias, normalización, colisiones, mensajes de error, historial, auditoría y compatibilidad hacia atrás.
