## PARTE I — TEORÍA

### 1.1. Origen y propósito

Medir el desempeño arquitectónico de ARKI contra **arquitectos humanos reales** es el único test riguroso de valor. Sin esto, ARKI es solo "otro generador".

**Objetivos:**

- Medir en qué ARKI es competitivo.
- Medir en qué ARKI es superior.
- Medir en qué ARKI es inferior.
- Aprender de arquitectos reales.
- Identificar sesgos en ARKI.

Referencias:

- Cross, N. (2011). *Design Thinking*.
- Lawson, B. (2006). *How Designers Think*.
- Dorst, K. (2015). *Frame Innovation*.
- Goldschmidt, G. (2014). *Linkography*.
- Gero, J. & Kannengiesser, U. (2004). *The Situated Function-Behaviour-Structure Framework*.

### 1.2. Protocolos de estudio

**A. Think-aloud protocols:**

- Arquitecto diseña hablando.
- Grabación + transcripción + análisis.
- Revela proceso cognitivo.

**B. Retrospective protocols:**

- Arquitecto diseña.
- Después explica decisiones.
- Menos invasivo.

**C. Comparative design studies:**

- Mismo brief a N arquitectos + ARKI.
- Comparación de resultados.
- Métricas objetivas + evaluación experta.

**D. Longitudinal studies:**

- Seguir proyectos reales.
- Documentar evolución.
- Identificar decisiones críticas.

**E. Protocol analysis (Goldschmidt):**

- Linkography: red de movimientos de diseño.
- Identifica fases críticas.
- Compara patrones.

### 1.3. Métricas de comparación

**Métricas objetivas:**

- Program compliance.
- Eficiencia espacial.
- Daylight autonomy.
- Energy use.
- Costo.
- Tiempo de diseño.
- Novedad (distancia al corpus existente).
- Utilidad (satisfacción de constraints).

**Métricas subjetivas (panel experto):**

- Calidad arquitectónica.
- Coherencia.
- Originalidad.
- Adecuación cultural.
- Constructabilidad.
- Belleza (si es medible).

**Métricas de proceso:**

- Número de iteraciones.
- Tiempo por decisión.
- Uso de referencias.
- Exploración de alternativas.
- Convergencia.

### 1.4. Desafíos

- **Sesgo de evaluador:** expertos prefieren lo humano.
- **Sesgo de brief:** algunos problemas favorecen a ARKI.
- **Sesgo de muestra:** arquitectos no representan diversidad.
- **Ética:** no reemplazar arquitectos.
- **Medición de "buena arquitectura"** es intrínsecamente subjetiva.

### 1.5. Protocolo de evaluación ciega

**Diseño:**

1. Reclutar 30 arquitectos + ARKI.
2. Dar mismo brief a todos.
3. Recoger outputs sin identificar autor.
4. Panel de 10 expertos evalúa a ciegas.
5. Métricas objetivas se calculan independientemente.
6. Análisis estadístico.

**Rigor:**

- Doble ciego cuando sea posible.
- Múltiples evaluadores por output.
- Inter-rater reliability (Cohen's kappa).
- Análisis cualitativo + cuantitativo.

### 3.1. Comparación estadística

```
compareArkiVsArchitects(arkiMetrics, architectsMetrics): Comparison[]
  comparisons = []
  
  for metric in commonMetrics:
    arkiValue = arkiMetrics[metric]
    architectsValues = architectsMetrics.map(m => m[metric])
    
    architectsMean = mean(architectsValues)
    architectsStd = std(architectsValues)
    
    # Percentil de ARKI en la distribución de arquitectos
    if betterDirection(metric) == 'up':
      percentileRank = count(architectsValues.filter(v => v <= arkiValue)) / architectsValues.length * 100
    else:
      percentileRank = count(architectsValues.filter(v => v >= arkiValue)) / architectsValues.length * 100
    
    # Significancia estadística
    zScore = (arkiValue - architectsMean) / architectsStd
    pValue = 2 * (1 - normalCDF(abs(zScore)))  # two-tailed
    
    conclusion = 
      percentileRank >= 75 and pValue < 0.05 ? 'arki_better' :
      percentileRank <= 25 and pValue < 0.05 ? 'architects_better' :
      'comparable'
    
    comparisons.push({
      metric,
      arkiValue,
      architectsMean,
      architectsStd,
      percentileRank,
      betterDirection: betterDirection(metric),
      conclusion
    })
  
  return comparisons
```

### 3.2. Inter-rater reliability

text

```
computeInterRaterReliability(evaluations): Reliability
  # Krippendorff's Alpha
  # Para ratings ordinales
  
  # Matriz de ratings: filas = submissions, columnas = evaluadores
  matrix = buildRatingsMatrix(evaluations)
  
  # Observed disagreement
  Do = computeObservedDisagreement(matrix)
  
  # Expected disagreement
  De = computeExpectedDisagreement(matrix)
  
  alpha = 1 - Do / De
  
  # Cohen's Kappa (para 2 evaluadores)
  kappa = computeCohenKappa(evaluations)
  
  interpretation = 
    alpha >= 0.8 ? 'excellent' :
    alpha >= 0.667 ? 'acceptable' :
    alpha >= 0.5 ? 'moderate' :
    'poor'
  
  return { krippendorffAlpha: alpha, cohensKappa: kappa, interpretation }
```

### 3.3. Análisis de linkografía

text

```
analyzeLinkography(submission): LinkographyAnalysis
  # Linkograph: red de movimientos
  # Identifica:
  # - Movimientos creativos (muchos links)
  # - Movimientos críticos (pocos links)
  # - Fases (clusters)
  
  linkograph = submission.linkography
  
  # Métricas
  totalMoves = linkograph.nodes.filter(n => n.kind == 'move').length
  totalLinks = linkograph.links.length
  
  # Densidad de links
  density = totalLinks / (totalMoves * (totalMoves - 1) / 2)
  
  # Movimientos críticos (grado alto)
  criticalMoves = linkograph.nodes
    .filter(n => n.kind == 'move')
    .map(n => ({ node: n, degree: countLinks(n, linkograph) }))
    .sortBy(degree desc)
    .slice(0, 5)
  
  # Fases (clusters)
  clusters = detectClusters(linkograph)
  
  return {
    totalMoves,
    totalLinks,
    density,
    criticalMoves,
    phaseCount: clusters.length,
    interpretation: interpret(linkograph)
  }
```

# CAPACIDAD 55 — GENERACIÓN ADVERSARIAL

# ═══════════════════════════════════════════════════

## PARTE I — TEORÍA

### 1.1. Origen y propósito

La **generación adversarial** crea problemas diseñados específicamente para **romper** los algoritmos de ARKI. Identifica:

- Casos límite.
- Debilidades estructurales.
- Inconsistencias.
- Supuestos inválidos.
- Bugs latentes.

Referencias:

- Goodfellow, I. et al. (2014). *Generative Adversarial Networks*.
- Madry, A. et al. (2017). *Towards Deep Learning Models Resistant to Adversarial Attacks*.
- Carlini, N. & Wagner, D. (2017). *Adversarial Examples*.
- Myers, G. (1979). *The Art of Software Testing* (metodología adversarial).

### 1.2. Tipos de adversariales

**Para arquitectura/BIM:**

1. **Geométricos:**
   - Formas no-euclidianas.
   - Geometrías degeneradas.
   - Escalas extremas (nanómetro, kilómetro).
   - Rotaciones no ortogonales.
   - Auto-intersecciones.
2. **Topológicos:**
   - Grafos desconectados.
   - Ciclos infinitos.
   - Árboles degenerados.
   - Islas imposibles.
3. **Semánticos:**
   - Contradicciones entre documentos.
   - Etiquetas incorrectas.
   - Categorías inexistentes.
   - Atributos contradictorios.
4. **Normativos:**
   - Cumplimiento imposible.
   - Normas contradictorias.
   - Umbrales límite.
   - Excepciones mal aplicadas.
5. **Estructurales:**
   - Cargas imposibles.
   - Materiales inexistentes.
   - Secciones degeneradas.
   - Inestabilidad garantizada.
6. **Ambientales:**
   - Clima extremo.
   - Datos inconsistentes.
   - Series temporales corruptas.
7. **De dominio:**
   - Programas inusuales.
   - Tipologías mixtas.
   - Usos imposibles.
8. **De recurso:**
   - Modelos gigantes.
   - Muchas iteraciones.
   - Baja memoria.
9. **De concurrencia:**
   - Edits simultáneos conflictivos.
   - Locks imposibles.
10. **De seguridad:**
    - Inputs maliciosos.
    - Inyección de datos.
    - DoS.

### 1.3. Estrategias de generación

**A. Mutation-based:**

- Tomar un caso válido.
- Aplicar mutaciones.
- Ver si rompe.

**B. Constraint-based:**

- Definir constraints al revés.
- Generar casos que violan.
- Ver cómo responde.

**C. Grammar-based:**

- Usar gramáticas (C11) invertidas.
- Generar formas inválidas.

**D. Search-based:**

- Búsqueda activa de casos que fallan.
- Objetivo: maximizar error.

**E. ML-based:**

- GAN entrenada contra ARKI.
- Genera casos adversariales.

**F. Fuzzing:**

- Random input masivo.
- Detectar crashes.

**G. Symbolic execution:**

- Ejecución simbólica de código.
- Encontrar paths no manejados.

**H. Metamorphic:**

- Transformaciones que preservan propiedades.
- Ver si ARKI las respeta.

### 1.4. Métricas

**Para cada caso adversarial:**

- **Detectado:** sí/no.
- **Manejado:** correctamente (error tipado) o no (crash).
- **Severidad:** crítica, mayor, menor, cosmética.
- **Root cause:** qué falló.

**Agregado:**

- Adversarial pass rate.
- Severity distribution.
- Coverage de paths.

### 1.5. Uso en ARKI

**Continua:**

- Antes de cada release.
- En CI/CD.
- Como parte de testing.

**Dirigida:**

- Antes de demos.
- Después de grandes cambios.
- En auditorías.

fuzz(targetFunction, inputSchema, iterations): AdversarialCase[]
  cases = []
  
  for i in 1..iterations:
    # Generar input aleatorio válido por schema
    randomInput = generateRandomInput(inputSchema)
    
    # Ejecutar en sandbox
    result = executeWithTimeout(targetFunction, randomInput, 5000)

searchAdversarial(targetFunction, seedInput, iterations): AdversarialCase[]
  # Búsqueda de inputs que maximizan error
  current = seedInput
  bestError = 0
  cases = []
  
  for i in 1..iterations:
    # Generar vecino
    neighbor = mutateInput(current)
    
    # Ejecutar
    result = executeWithTimeout(targetFunction, neighbor, 5000)
    error = computeError(result)
    
    if error > bestError:
      bestError = error
      current = neighbor
      cases.push({
        id: generateId(),
        category: 'unknown',
        description: `Input adversarial encontrado (error ${error})`,
        input: neighbor,
        outcome: result.timedOut ? 'timeout' : result.threw ? 'crash' : 'silently_wrong',
        severity: classifySeverity(error),
        generatedBy: 'search'
      })
    else if random() < 0.1:  # Simulated annealing
      current = neighbor
  
  return cases
```

metamorphicTest(targetFunction, transformations): AdversarialCase[]
  cases = []
  
  for transformation in transformations:
    # Generar caso base
    baseInput = generateValidInput()
    baseOutput = targetFunction(baseInput)
    
    # Transformar
    transformedInput = transformation.apply(baseInput)
    transformedOutput = targetFunction(transformedInput)
    
    # Verificar propiedad metamórfica
    expectedRelation = transformation.expectedRelation(baseOutput)
    actualRelation = transformedOutput
    
    if not relationHolds(expectedRelation, actualRelation):
      cases.push({
        id: generateId(),

## PARTE I — TEORÍA

### 1.1. Origen y propósito

**Meta-learning** = "aprender a aprender". Un sistema que mejora con la experiencia acumulada, no solo en una tarea, sino en **cómo abordar nuevas tareas**.

**Aplicación ARKI:** después de N proyectos, ARKI debería:

- Reconocer patrones recurrentes.
- Transferir conocimiento entre tipologías.
- Mejorar sus heurísticas.
- Identificar sus propias debilidades.

Referencias:

- Schmidhuber, J. (1987). *Evolutionary principles in self-referential learning*.
- Thrun, S. & Pratt, L. (1998). *Learning to Learn*.
- Finn, C. et al. (2017). *Model-Agnostic Meta-Learning (MAML)*.
- Hospedales, T. et al. (2020). *Meta-Learning in Neural Networks*.
- Vanschoren, J. (2018). *Meta-Learning: A Survey*.

### 1.2. Tipos de meta-learning

**A. Metric-based:**

- Aprende una distancia.
- Prototypical Networks, Matching Networks.

**B. Model-based:**

- Aprende un modelo que se adapta rápido.
- Memory-Augmented Neural Networks.

**C. Optimization-based:**

- MAML: encuentra inicialización óptima.
- Reptile.

**D. Non-parametric:**

- Meta-features + algoritmos de selección.
- Aprendizaje basado en experiencia acumulada.

**E. Bayesian:**

- Priors aprendidos de experiencia.
- Actualización bayesiana.

**F. Reinforcement Learning meta:**

- Aprende política de aprendizaje.

### 1.3. Aplicaciones a ARKI

**A. Selección de algoritmo:**

- Dado un problema de layout, ¿cuál algoritmo usar? (Spatial Syntax vs GA vs SA vs gramática).

**B. Selección de features:**

- Dado un problema, ¿qué features son relevantes?

**C. Learning from mistakes:**

- Cada error detectado se convierte en regla.

**D. Transfer entre tipologías:**

- Lo aprendido en hospitales → aplicable a colegios.

**E. Auto-curriculum:**

- ARKI se auto-impone problemas progresivamente más difíciles.

**F. Meta-optimización:**

- Ajustar hiperparámetros de todos los algoritmos.

### 1.4. Meta-features

**Características del problema:**

- Tipología.
- Tamaño (área, cantidad de espacios).
- Complejidad (constraints, número de relaciones).
- Similitud con problemas previos.
- Nivel de certidumbre.

**Características del resultado:**

- Calidad obtenida.
- Tiempo de cómputo.

recommendAlgorithm(problem, model): Recommendation
  # 1. Buscar experiencias similares
  similar = findSimilarExperiences(problem, model.experiences)
  
  # 2. Patrones aplicables
  applicablePatterns = model.patterns.filter(p => matchesCondition(p.conditions, problem))
  
  # 3. Anti-patrones que aplican
  applicableAntiPatterns = model.antiPatterns.filter(ap => matchesCondition(ap.conditions, problem))
  
  # 4. Votación ponderada
  votes = {}
  for s in similar:
    exp = findExperience(s.experienceId)
    weight = s.similarity * (exp.outcome == 'success' ? 1 : exp.outcome == 'partial' ? 0.5 : 0)
    votes[exp.algorithmChosen] = (votes[exp.algorithmChosen] || 0) + weight
  
  for p in applicablePatterns:
    weight = p.successRate * log(p.sampleSize + 1)
    votes[p.recommendation.algorithm] = (votes[p.recommendation.algorithm] || 0) + weight
  
  # 5. Eliminar algoritmos en anti-patrones
  for ap in applicableAntiPatterns:
    for algo in Object.keys(votes):
      if ap.problem.includes(algo):
        votes[algo] *= 0.1
  
  # 6. Mejor
  best = max(votes.entries())
  bestAlgorithm = best.key
  
  # 7. Parámetros
  params = aggregateParameters(similar, bestAlgorithm)
  
  # 8. Confidence
  confidence = computeConfidence(similar, applicablePatterns)
  
  return {
    recommendedAlgorithm: bestAlgorithm,
    recommendedParameters: params,
    confidence,
    alternatives: buildAlternatives(votes, similar),
    similarExperiences: similar,
    reasoning: buildReasoning(similar, applicablePatterns, applicableAntiPatterns)
  }

### 3.3. Aprendizaje de patrones

extractPatterns(experiences): Patterns
  # Agrupar por outcome
  successes = experiences.filter(e => e.outcome == 'success')
  
  patterns = []
  
  # Clustering por features similares
  clusters = clusterBySimilarity(successes, threshold=0.8)
  
  for cluster in clusters:
    # Si un cluster tiene > 5 casos con mismo algoritmo
    algorithms = cluster.map(e => e.algorithmChosen)
    mostCommon = mode(algorithms)
    frequency = count(algorithms, mostCommon) / len(cluster)
    
    if frequency > 0.7 and len(cluster) >= 5:
      # Patrón
      patterns.push({
        id: generateId(),
        conditions: extractCommonConditions(cluster),
        recommendation: {
          algorithm: mostCommon,
          parameters: meanParameters(cluster.filter(e => e.algorithmChosen == mostCommon))
        },
        successRate: mean(cluster.map(e => e.result.quality)),
        sampleSize: len(cluster)
      })
  
  # Anti-patrones: clusters de failures
  failures = experiences.filter(e => e.outcome == 'fail')
  failureClusters = clusterBySimilarity(failures, 0.8)
  
  antiPatterns = failureClusters.filter(c => len(c) >= 5).map(c => ({
    id: generateId(),
    conditions: extractCommonConditions(c),
    problem: mostCommonProblem(c),
    sampleSize: len(c)
  }))
  
  return { patterns, antiPatterns }

metaOptimize(algorithm, experiences): OptimalParameters
  # Encontrar parámetros que maximizan calidad promedio
  
  # 1. Filtrar experiencias con este algoritmo
  relevantExp = experiences.filter(e => e.algorithmChosen == algorithm)
  
  if len(relevantExp) < 20:
    return { status: 'insufficient_data', warning: '< 20 experiences' }
  
  # 2. Grid search / random search sobre parámetros
  bestParams = null
  bestScore = -Infinity
  
  parameterSpace = getParameterSpace(algorithm)
  
  for params in sample(parameterSpace, 100):
    # Filtrar experiencias con estos params (dentro de tolerancia)
    matchingExp = relevantExp.filter(e => parametersMatch(e.algorithmParameters, params, 0.1))
    
    if len(matchingExp) < 5:
      continue
    
    score = mean(matchingExp.map(e => e.result.quality))
    
    if score > bestScore:
      bestScore = score
      bestParams = params
  
  # 3. Bayesian optimization refinamiento
  if bestParams:
    bestParams = bayesianRefine(algorithm, relevantExp, bestParams, iterations=50)
  
  return {
    status: 'completed',
    optimalParameters: bestParams,
    expectedQuality: bestScore,
    sampleSize: relevantExp.length
  }

# CAPACIDAD 57 — TRANSFER LEARNING

# ═══════════════════════════════════════════════════

## PARTE I — TEORÍA

### 1.1. Origen y propósito

**Transfer Learning** = aprovechar conocimiento de un dominio para mejorar desempeño en otro dominio **relacionado pero distinto**.

**Aplicación ARKI:**

- Aprendizaje de hospitales → transferido a clínicas.
- Aprendizaje de oficinas → transferido a coworking.
- Aprendizaje de viviendas → transferido a hoteles pequeños.

Referencias:

- Pan, S. & Yang, Q. (2010). *A Survey on Transfer Learning*.
- Zhuang, F. et al. (2020). *A Comprehensive Survey on Transfer Learning*.
- Yosinski, J. et al. (2014). *How transferable are features in deep neural networks?*.

### 1.2. Tipos

**A. Inductive transfer:**

- Dominios diferentes, tareas iguales.
- Ej: hospitales → clínicas.

**B. Transductive transfer:**

- Dominios diferentes, tareas diferentes pero relacionadas.
- Ej: layout → estructura.

**C. Unsupervised transfer:**

- Sin etiquetas en domain target.

**D. Negative transfer:**

- Transferir empeora (riesgo).

### 1.3. Estrategias

**A. Instance transfer:**

- Reusar instancias de domain source.
- Ponderar por similitud.

**B. Feature transfer:**

- Compartir representaciones.
- Fine-tuning de features.

**C. Parameter transfer:**

- Compartir parámetros iniciales.
- Fine-tuning.

**D. Relational transfer:**

- Compartir relaciones entre dominios.

### 1.4. Métricas

- **Transfer gain:** mejora vs entrenar desde cero.
- **Negative transfer rate:** casos donde transfer empeora.
- **Sample efficiency:** datos necesarios con/sin transfer.

transfer(request): TransferResult
  # 1. Medir similitud entre dominios
  similarity = computeDomainSimilarity(source, target)
  
  if similarity < 0.3:
    return {
      transferGain: 0,
      negativeTransferDetected: true,
      warnings: ['Dominios demasiado diferentes']
    }
  
  # 2. Estrategia
  strategy = request.strategy == 'auto' ? selectStrategy(similarity, source, target) : request.strategy
  
  match strategy:
    case 'instance':
      result = instanceTransfer(source, target)
    case 'feature':
      result = featureTransfer(source, target)
    case 'parameter':
      result = parameterTransfer(source, target)
    case 'relational':
      result = relationalTransfer(source, target)
  
  # 3. Baseline sin transfer
  baseline = trainFromScratch(target)
  
  # 4. Con transfer
  withTransfer = trainWithTransfer(target, result.transferredData)
  
  # 5. Gain
  gain = (withTransfer.quality - baseline.quality) / baseline.quality * 100
  
  # 6. Negative transfer
  negativeTransfer = gain < 0
  negativeTransferPct = negativeTransfer ? abs(gain) : 0
  
  return {
    transferGain: gain,
    transferredSamples: result.transferredSamples,
    fineTuned: result.fineTuned,
    negativeTransferDetected: negativeTransfer,
    negativeTransferPct,
    recommendations: buildRecommendations(gain, similarity, source, target),
    warnings: negativeTransfer ? ['Negative transfer detectado'] : []
  }

### 1.2. Tipos de explicación

**A. Local:** para una decisión específica.

- SHAP values.
- LIME.
- Counterfactual.

**B. Global:** comportamiento general del modelo.

- Feature importance.
- Partial dependence plots.
- Surrogate models.

**C. Causal:** relaciones causa-efecto.

- Causal inference.
- Do-calculus.

**D. Basada en ejemplo:** casos similares.

- Prototypes.
- Counterfactuals.

### 1.3. Contrafactuales

**Definición:** "¿Qué cambio mínimo en el input habría llevado a otro output?"

**Tipos:**

- **Contrastivos:** "en vez de X, sería Y si..."
- **Feasibles:** cambios realizables.
- **Accionables:** que el usuario puede hacer.

**Ejemplo ARKI:**
"Este layout tiene eficiencia 0.42. Si el baño estuviera en otro lugar (2m más al norte), la eficiencia subiría a 0.55."

### 1.4. Explicaciones arquitectónicas

No solo números. **Razonamiento arquitectónico** explícito:

- "El espacio tiene baja integración porque..."
- "La circulación es ineficiente porque..."
- "El daylight es insuficiente porque..."

**Cada explicación incluye:**

- Afirmación.
- Evidencia.
- Fuente (método, elemento).
- Alternativas consideradas.
- Recomendación.

generateCounterfactual(model, input, target, desiredOutput): Counterfactual
  # 1. Encontrar cambio mínimo
  currentOutput = model.predict(input)
  
  # 2. Optimización para encontrar input' tal que predict(input') = desiredOutput
  # Minimizar || input' - input ||_1
  # Sujeto a: predict(input') = desiredOutput
  # Y features deben ser factibles
  
  result = optimize(
    objective = || input' - input ||_1,
    constraint = predict(input') == desiredOutput,
    bounds = featureBounds
  )
  
  # 3. Generar explicación
  changes = diff(input, result.inputPrime)
  
  return {
    description: `Si ${changes.map(c => `${c.feature} ${c.from}→${c.to}`).join(', ')}, ` +
                 `el output sería ${desiredOutput}`,
    changes,
    expectedOutcome: desiredOutput,
    feasible: isFeasible(changes)
  }
```

### 3.2. Detección de regresiones

detectRegressions(run, baseline): Regression[]
  regressions = []
  
  for test in run.results:
    baselineTest = baseline.results.find(t => t.testId == test.testId)
    if not baselineTest: continue
    
    if baselineTest.status == 'pass' and test.status == 'fail':
      regressions.push({
        testId: test.testId,
        previousStatus: 'pass',
        currentStatus: 'fail',
        severity: classifySeverity(test, baselineTest)
      })
  
  return regressions

classifySeverity(test, baselineTest):
  # Crítico si es test de módulo core
  if test.testId.startsWith('core.') or test.testId.startsWith('structural.'):
    return 'critical'
  # Mayor si es de UI o capacidad
  if test.testId.startsWith('ui.') or test.testId.startsWith('capability.'):
    return 'major'
  return 'minor'
```

evaluateCapabilities(runs): CapabilityHealth[]
  # Agrupar tests por capacidad
  capabilities = {}
  
  for run in runs:
    for test in run.results:
      capId = extractCapability(test.testId)
      if not capId: continue
      
      if not capId in capabilities:
        capabilities[capId] = { pass: 0, fail: 0, skip: 0, lastEvaluated: run.completedAt }
      
      capabilities[capId][test.status]++
  
  # Score
  health = []
  for capId, stats in capabilities:
    total = stats.pass + stats.fail + stats.skip
    score = stats.pass / total * 100
    
    status = 
      score >= 95 ? 'healthy' :
      score >= 80 ? 'degraded' :
      'critical'
    
    issues = []
    if stats.fail > 0:
      issues.push(`${stats.fail} tests fallidos`)
    if stats.skip > total * 0.2:
      issues.push('Cobertura insuficiente')
    
    health.push({
      capabilityId: capId,
      status,
      lastEvaluated: stats.lastEvaluated,
      coverage: (stats.pass + stats.fail) / total,
      score,
      issues
    })
  
  return health
```
