======================================================================
3. EL ESQUELETO
======================================================================

D-2 es el ESQUELETO arquitectónico.

Definición consolidada:

D-2 = única representación semántica canónica del edificio/proyecto que ARKI
considera vigente en un instante.

D-2 NO es:
- dibujo;
- imagen;
- razonamiento;
- parti;
- candidato;
- DeveloperProposal;
- SpatialHypothesis;
- UI ProjectState.

D-2 debe evolucionar gradualmente hacia un modelo corporal suficiente para
representar arquitectura, pero NO se deben agregar tipos porque un diagrama los
sugiera.

Antes de ampliar D-2:
1. verificar tipos existentes;
2. verificar relaciones existentes;
3. demostrar gap real;
4. extender sólo si es necesario.

Modelo conceptual objetivo:

PROJECT
├── SITE
├── BUILDING / ORGANIZATION
│   ├── LEVEL
│   ├── ZONE
│   ├── SPACE
│   ├── CIRCULATION
│   ├── BOUNDARY / WALL
│   ├── OPENING / DOOR / WINDOW
│   └── STRUCTURAL / OTHER SYSTEM ELEMENTS
└── SYSTEMS / RELATIONSHIPS

IMPORTANTE:
Este árbol es MODELO CONCEPTUAL DE DISCUSIÓN.
NO autoriza crear inmediatamente BUILDING, LEVEL, ZONE, CIRCULATION u otros
ElementKind nuevos. El D-2 real observado actualmente debe seguir siendo el
contrato de implementación hasta demostrar el gap.

======================================================================
4. EL SISTEMA NERVIOSO
======================================================================

La propuesta consolidada amplía "sistema nervioso" más allá de conexiones HTTP.

El sistema nervioso de ARKI es:

EVENT
  ↓
DERIVATION
  ↓
DEPENDENCY
  ↓
IMPACT
  ↓
VALIDITY
  ↓
REACTION
  ↓
SELECTIVE RECOMPUTATION
  ↓
NEW STATE / NEW PROPOSAL / HUMAN REVIEW

Cada entidad relevante debe poder responder, según aplique:
- quién/qué la originó;
- de qué depende;
- qué evidencia la soporta;
- qué estado epistémico tiene;
- qué versión tiene;
- qué se afecta si cambia;
- qué debe recomputarse;
- qué requiere decisión humana.

Ejemplo causal:

CLIENT REQUIREMENT
"3 dormitorios"
      ↓
PROGRAM REQUIREMENT
      ↓
FUNCTIONAL RELATIONSHIPS
      ↓
SPACES
      ↓
GEOMETRY
      ↓
BOUNDARIES / OPENINGS
      ↓
STRUCTURAL / ENVIRONMENTAL CONSEQUENCES
      ↓
REPRESENTATION

Si 3 cambia a 4:
ARKI no debe sólo reemplazar un número.
Debe recorrer el grafo de impacto y recomputar únicamente lo afectado.

Este comportamiento es la esencia del "sistema nervioso".

5. LOS CUATRO UNIVERSOS QUE NO DEBEN CONFUNDIRSE
======================================================================

1. KNOWLEDGE
   Lo que ARKI sabe.
   Normas, precedentes, tipologías, materiales, sistemas, sitio, memoria.

2. REASONING
   Lo que ARKI piensa.
   Problema, hipótesis, análisis, crítica, transferencia, explicación.

3. PROPOSALS
   Lo que ARKI imagina/desarrolla.
   Parti candidates, SpatialHypothesis, Candidate, DeveloperProposal.

4. ARCHITECTURAL STATE
   Lo que actualmente constituye el proyecto.
   D-2.

Flujo de autoridad:

KNOWLEDGE
    ↓
BRAIN / REASONING
    ↓
PROPOSALS
    ↓
HUMAN + VALIDATION
    ↓
D-2

Nada debe saltar directamente de "idea" a "arquitectura canónica".

8. CINCO REDES SUPERPUESTAS
======================================================================

Un proyecto no debe entenderse como una sola topología.

A. FUNCTIONAL NETWORK
   activities / requirements / adjacency / separation / dependency.

B. CIRCULATION NETWORK
   access / paths / public / service / vertical / accessibility.

C. SPATIAL NETWORK
   contains / adjacent / overlaps / separates / connects.

D. PHYSICAL NETWORK
   boundaries / hosts / openings / support / enclosure.

E. CAUSAL NETWORK
   requirement → reasoning → decision → space → geometry → element.

Futuro:
- structural network;
- environmental network;
- services network;
- cost/construction network.

Estas redes deben poder cruzarse mediante identidad/provenance sin convertirse
en estados canónicos paralelos.

18. DEVELOPER PROMOTION — CONTRATO CONSOLIDADO
======================================================================

No aceptar como verdad simplemente:
proposalId + proposedElements + humanReviewId.

Flujo más seguro:

1. Core recibe proposal y lo persiste como reasoning event.
2. Core devuelve proposal/execution ID + fingerprint.
3. Human Review referencia exactamente ese proposal ID/fingerprint.
4. Promotion recibe:
   - proposalId
   - proposalFingerprint
   - humanReviewId
   - humanAuthorityRef
5. Core recupera propuesta persistida.
6. Core verifica fingerprint.
7. Core verifica HumanReview APPROVED para ESA propuesta.
8. Core valida DTO/schema.
9. Core convierte DTO → tipos internos.
10. Core ejecuta A002/ArchiTransaction/H-chain aplicable.
11. Si todo pasa: commit D-2.
12. Si falla: cero mutación.
13. Event log registra resultado.

Esto cierra riesgo de TOCTOU/payload substitution entre aprobación y promoción.

26. VEREDICTO CONSOLIDADO
======================================================================

La propuesta de DeepSeek es una base técnicamente útil y converge en gran parte
con la propuesta de ChatGPT.

SE ADOPTA:
- separación UI / orchestration / kernel;
- D-2 único;
- event log único;
- DeveloperProposal;
- mutation D-2 sólo en Core;
- reasoning-executions append-only;
- Human Authority;
- microcaso explícito;
- commits pequeños;
- reuse-first.

SE MODIFICA:
- Exploration deja de tratarse como capa inferior lineal;
- "sólo capas adyacentes" deja de ser ley absoluta;
- sistema nervioso no es sólo HTTP: es causalidad + impacto + reacción +
  recomputación;
- Developer no es mero conversor, sino motor iterativo de desarrollo;
- promotion debe ligar criptográficamente review con proposal persistida;
- "nada existente se toca" se sustituye por "no duplicar; corregir/extender
  cuando haya gap";
