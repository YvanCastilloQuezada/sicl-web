# ARKI-SOLVER-MAP-001 — Structural FEM and Geotechnical Analysis

**Research family:** Structural finite-element method (FEM) and geotechnical analysis  
**Candidates compared:** OpenSees/OpenSeesPy, CalculiX, Code_Aster, and PLAXIS  
**Access date for all sources:** 2026-09-24  
**Scope boundary:** This report evaluates solver families for reproducible, automatable engineering analysis. It does not install software, execute a solver, or use Aurora artifacts. Where the consulted primary sources do not establish a fact, the report states **UNKNOWN**.

## Executive conclusion

The candidates are not interchangeable. **OpenSees/OpenSeesPy** is the strongest fit for script-first structural and earthquake/geotechnical research workflows, with a documented Python interpreter, Tcl/OpenSees applications, structural and geotechnical examples, and explicit verification guidance. Its license is permissive for education, research, non-profit noncommercial use, and internal use, but commercial redistribution requires a University of California license; it is therefore not equivalent to a standard unrestricted permissive license. OpenSees is explicitly described by its own documentation as research software supplied without warranty, so a professional design workflow needs independent engineering review and project-specific validation.[1] [2] [3] [4] [5]

**Code_Aster** is the strongest open-source general-purpose engineering candidate when breadth, geomechanics, coupled physics, industrial-scale validation, and a first-class batch/test harness matter more than a low learning curve. The official product page reports GPL distribution, geomechanics and soil–structure interaction, Python-based extensibility, MUMPS/PETSc integration, systematic regression testing, and several thousand daily test cases. The official `run_aster` documentation provides command-line, Python, MPI, and CTest execution paths. Its main practical limitation is workflow complexity: the reviewed sources establish a rich Python/batch architecture, but do not establish a simple high-level Python modeling API comparable to OpenSeesPy.[6] [7] [8]

**CalculiX** is a useful open-source structural and multiphysics command-line solver for linear/nonlinear, static/dynamic, and thermal work. It has a GPL license, a documented Abaqus-like input format, and a large distribution of verification examples with reference result files. It is less directly aligned with geotechnical constitutive modeling than OpenSees or PLAXIS in the sources reviewed; the official site and manual emphasize general structural/field problems rather than a soil-specialist product. No official Python API was verified.[9] [10] [11] [12]

**PLAXIS** is the strongest specialist fit for professional geotechnical analysis and soil–structure workflows, but it is proprietary commercial software. Bentley’s official sources establish subscription licensing, proprietary object-code licensing, restrictions on commercial hosting, Python scripting/remote scripting, command-line support for PLAXIS SoilTest, interactive scripting documentation, and a published verification-case taxonomy covering soil, structural, groundwater/consolidation, thermal, and dynamics cases. It is the best candidate where professional geotechnical feature depth and vendor support outweigh open-source inspection, self-hosting freedom, and license cost. The reviewed sources do not establish that the full PLAXIS solver can be run as a freely redistributable, license-free headless service; treat that as **not available under the consulted license terms** rather than as an open-source capability.[13] [14] [15] [16] [17]

For an ARKI integration layer, the recommended architecture is **adapter-based rather than solver-specific**: use OpenSeesPy for transparent scripted structural/seismic studies, Code_Aster for broad open-source engineering and coupled analyses, CalculiX for conventional structural FEM and regression fixtures, and PLAXIS only where a licensed professional geotechnical workflow is explicitly required. None of these tools, by itself, establishes engineering approval, code compliance, or a substitute for a qualified engineer.

## Candidate analyses

### 1. OpenSees and OpenSeesPy

**Scope and technical identity.** The official documentation defines OpenSees as a framework for simulating the dynamic response of structural and geotechnical systems. It was originally developed for performance-based earthquake engineering and is also presented for fire, wind, earthquake, wave, tsunami, and storm-surge response. OpenSeesPy is documented as a Python 3 interpreter of OpenSees. The OpenSeesPy examples index explicitly separates structural, earthquake, tsunami, geotechnical, thermal, parallel, plotting, and sensitivity examples.[1] [3] [18]

**License and openness.** OpenSees is not safely classifiable as “unrestricted permissive open source” for all use cases. The official license page grants use, reproduction, modification, and distribution to educational, research, and non-profit entities for noncommercial purposes, and use and modification by other entities for internal purposes. It separately states that incorporating OpenSees into products for commercial distribution requires a license from UC Berkeley. The same page disclaims warranties and maintenance. OpenSeesPy’s official documentation and repository repeat the requirement for a similar license for commercial redistribution, including applications or cloud services using `import openseespy`.[2] [3] [4]

**Operating systems and languages.** The current OpenSees build documentation describes CMake builds across Windows, macOS, and Linux and names C, C++, Fortran, Tcl, and Python-related dependencies. The OpenSeesPy documentation states that version 3.8.0.0 is released for Linux, Windows, and Mac ARM64 and requires Python 3.12; the build page reviewed for the core project also contains version-specific build notes that mention Python 3.11. This version discrepancy is a release/documentation detail that must be resolved against the exact package version selected. The language/runtime facts are verified; a single universal version requirement is **UNKNOWN** across all OpenSees/OpenSeesPy releases.[3] [5]

**API, CLI, headless execution, and I/O.** OpenSees exposes interpreter commands and standalone applications; OpenSeesPy exposes Python calls such as `ops.model`, `ops.node`, `ops.element`, `ops.analysis`, `ops.analyze`, recorders, and response queries. The build documentation identifies OpenSees, OpenSeesMP, and OpenSeesPy artifacts. These script and interpreter modes are suitable for headless execution in an external process or Python worker. Inputs are code/text scripts and model commands; outputs can include recorder files and queried responses. Exact current binary names and packaging vary by release, so an adapter should inspect the installed version rather than hard-code paths.[1] [3] [5]

**Determinism.** No official source reviewed promises bitwise determinism. A controlled serial run with pinned version, dependencies, input script, random seeds where applicable, solver settings, and machine environment is a reasonable reproducibility protocol, but it is not a verified product guarantee. Parallel OpenSees variants and nonlinear convergence paths require extra care. This report therefore records determinism as **UNKNOWN**, not “deterministic.”

**Testing and validation.** The official verification page is unusually candid. It distinguishes verification against analytical/theoretical solutions from validation against physical experiments and warns that verification is not sufficient to establish that a model is correct for a particular real system. It describes dynamic black-box testing, some white-box unit/system testing, and examples covering elements, materials, solvers, integrators, algorithms, static, dynamic, and eigenvalue analyses. This is strong evidence for testability, but it is not a project-specific validation certificate.[18]

**Limitations and professional boundary.** OpenSees is powerful but modeling choices remain user-controlled. The official license says the program was developed for research purposes, is supplied “as is,” and should not be relied on exclusively. Therefore, an ARKI system may use it to generate analyses, compare scenarios, and produce auditable evidence, but it must not represent an OpenSees result as an approved structural or geotechnical design without qualified engineering review, governing-code checks, sensitivity studies, and project-specific validation.[2] [4] 

**C1–C80 relevance.** The direct relevance is **C06 Estructuras Profesionales** and **C62 Estructuras No Lineales + Performance-Based**. The earthquake/performance-based origin and nonlinear structural capabilities support C62; structural and geotechnical analysis support C06. C03 Física Térmica has only conditional relevance because OpenSeesPy lists thermal examples, but the candidate was not evaluated as a thermal-design solver. No direct evidence was found in the reviewed sources for C34–C43 interoperability/governance capabilities; those would be ARKI adapter responsibilities, not native solver claims.

### 2. CalculiX

**Scope and technical identity.** The official CalculiX site describes a finite-element package for field problems. Its solver performs linear and nonlinear calculations, including static, dynamic, and thermal solutions. The solver and interactive 3D pre/postprocessor can be used independently, and the solver uses an Abaqus input format. The repository identifies it as a three-dimensional structural finite-element program and points users to the theory reference by Dhondt.[9] [11]

**License and openness.** The official site states that CalculiX is free software under the GNU General Public License, and the official GitHub repository metadata identifies GPL-2.0. This is materially different from OpenSees’ research/internal/commercial-redistribution boundary: CalculiX is GPL software, subject to GPL obligations when distributing covered derivative works. The report does not infer that all surrounding GUI, wrappers, or third-party preprocessors share the same license.[9] [10]

**Operating systems and languages.** The official site states that the package is designed for Unix platforms including Linux and also runs on Microsoft Windows. The source repository is primarily Fortran according to repository metadata, while the complete implementation language mix was not exhaustively verified. Python is not identified by the official sources reviewed as a native modeling API. The language field should therefore be recorded as **Fortran-dominant; complete mix UNKNOWN**.[9] [10]

**API, CLI, headless execution, and I/O.** `ccx` is a solver executable driven by text input decks and produces solver result files; the official site says the solver can operate independently and uses Abaqus-style input. This is a strong CLI/headless fit. A Python API for model construction or official Python orchestration was not verified. Third-party wrappers exist in the ecosystem, but they are outside the primary official evidence boundary and are not treated as native CalculiX capabilities.[9] [12]

**Determinism and testability.** No determinism guarantee was found. The official manual’s verification section says the examples are simple cases suitable to test distinct features, can check whether an installation is correct, and have input files plus reference result files in the distribution. This makes CalculiX particularly attractive for regression tests: ARKI can preserve a deck, version, environment manifest, and expected result tolerance. Verification examples are not a substitute for validating a soil model or a project-specific design.[12]

**Limitations and professional boundary.** The official materials reviewed emphasize general structural/field FEM, thermal analysis, and examples such as a turbocharger/jet-engine investigation. They do not establish a soil-specialist constitutive library, geotechnical staging workflow, or geotechnical professional-validation framework comparable to PLAXIS. That does not prove CalculiX cannot model a particular geotechnical problem; it means the specialist capability was not verified from the selected primary sources. Use it for structural FEM and carefully scoped research benchmarks unless additional constitutive and validation evidence is collected.

**C1–C80 relevance.** CalculiX is directly relevant to **C06** for structural FEM and conditionally relevant to **C62** where its nonlinear structural features match the problem. C03 is conditionally relevant for thermal calculations. Geotechnical relevance is **limited/not established** in this review, so it should not be mapped to a dedicated geotechnical capability without further evidence.

### 3. Code_Aster

**Scope and technical identity.** Code_Aster’s official product page describes it as an EDF R&D numerical simulation package for mechanics and thermodynamics. It explicitly lists linear and nonlinear structural analysis, thermo-mechanical and thermo-hydro-mechanical coupling, geomechanics, soil–structure interaction, modal and dynamic analysis, nonlinear dynamics, seismic performance, fatigue, fracture, and limit-state analysis. It is therefore the broadest open-source candidate in this comparison for structural and geotechnical coverage.[6]

**License, openness, and development status.** The official product page states that Code_Aster is distributed under the GNU GPL and frames source access as a way to inspect assumptions, verify methods, and develop features. It describes more than 35 years of development, more than one million lines of code, 4,600 verification test cases on the official home page, several thousand test cases run daily on the product page, and systematic regression testing within an EDF quality-assurance process. These are official project claims, not independently reproduced measurements in this task.[6] [19]

**Operating systems and languages.** The source repository contains Fortran/C/C++/Python-oriented directories and build tooling, and the official documentation describes Python as central to management, automation, and extensibility. The sources reviewed do not provide one concise current operating-system support table; the exact supported OS matrix for the selected release is therefore **UNKNOWN**. A deployment plan should pin a published release/container or a maintained build recipe and record compiler/library versions.[7] [8]

**API, CLI, headless execution, and I/O.** Code_Aster can be used as a standard Python module. The `bin/run_aster` script executes studies from `.export` files on the command line, can run `.py` or `.comm` files directly, and supports MPI. The documentation also exposes `bin/run_ctest` for executing test cases through CTest, and Python classes for preparing work directories, copying files, executing studies, and collecting status. This is excellent evidence for headless orchestration and test harness integration. It is more accurate to describe Code_Aster as a Python-command/batch ecosystem than to promise a simple object-level modeling API.[8]

**Determinism.** The official sources do not promise bitwise or cross-platform determinism. Code_Aster supports parallel execution, multiple linear solvers, and complex nonlinear workflows; these are common reasons to treat exact reproducibility as an environment-and-settings question. Use versioned studies, fixed mesh and command files, explicit solver settings, captured `.export` files, controlled MPI/BLAS/MUMPS/PETSc versions, and tolerance-based result comparison. The formal field remains **UNKNOWN**.

**Testing, validation, and limitations.** The combination of thousands of official verification/regression tests, CTest integration, and documented engineering validation is a major strength. However, official quality claims do not validate every user model or guarantee that a chosen constitutive law, mesh, boundary condition, or load path is appropriate. The principal operational limitation is complexity: the adapter must manage Code_Aster’s study structure, command language, versioning, dependencies, working directories, and potentially MPI.

**Professional boundary.** Code_Aster’s official page positions it for high-stakes industrial studies, including energy, nuclear, civil engineering, transport, aerospace, and research, and describes EDF quality assurance. That is evidence of professional orientation, not an automatic project qualification. A qualified engineer still owns assumptions, load combinations, mesh convergence, model calibration, code compliance, and sign-off. GPL openness improves inspectability and self-hosting but does not transfer professional liability to the software project.[6]

**C1–C80 relevance.** Code_Aster has direct relevance to **C06 Estructuras Profesionales** and **C62 Estructuras No Lineales + Performance-Based**, with stronger conditional relevance to **C03 Física Térmica** due to thermo-mechanical and thermo-hydro-mechanical features. Its geomechanics and soil–structure interaction capabilities are directly relevant to the solver family but do not correspond to a separately named capability in the consulted C1–C80 matrix. C34–C43 should be treated as external ARKI integration/governance work unless separately verified.

### 4. PLAXIS 2D and PLAXIS 3D

**Scope and technical identity.** PLAXIS is the specialist geotechnical option in this comparison. Bentley’s official verification-case index organizes cases under soil elastic, soil elastoplastic, structural, groundwater and consolidation, thermal, and dynamics categories. The PLAXIS 2D reference manual is identified as a special-purpose two-dimensional finite-element program for deformation, stability, and flow analysis. These sources support a direct geotechnical and soil–structure fit.[13] [16]

**License and openness.** Bentley’s EULA states that the software is proprietary, licensed rather than sold, and subject to a non-exclusive right to install and use a copy for production use. It prohibits renting, lending, commercial hosting, and fee- or transaction-based services unless alternate pricing is arranged. Bentley’s product documentation states that PLAXIS uses subscription entitlement service for licensing, activation, and updates. PLAXIS is therefore **commercial/proprietary, not open source**.[14] [15]

**Operating systems and languages.** The reviewed official sources establish a GUI product, Python scripting, remote scripting, command/object references, and Jupyter-based interactive documentation. They do not expose a concise current OS support table in the fetched pages. The precise supported OS matrix is **UNKNOWN** in this report. Python is verified as the scripting language; the internal implementation language is **UNKNOWN**.

**API, CLI, headless execution, and I/O.** Bentley documents Python automation and a scripting layer, and the PLAXIS release documentation explicitly states that PLAXIS SoilTest supports command line and remote scripting. The same release documentation adds an interactive Python/Jupyter documentation layer. This supports automation of model creation, calculations, and result extraction, but the consulted sources do not establish that all PLAXIS 2D/3D calculations can be run as an unrestricted standalone headless binary. Treat full headless operation as **qualified/partially verified**, and require a licensed product test for the exact workflow.

**Determinism and testability.** No deterministic-execution guarantee was found. Vendor verification cases are strong evidence that Bentley publishes benchmark/verification material for the product’s soil, structural, groundwater/consolidation, thermal, and dynamic functions. They do not guarantee identical results across every version, license tier, solver setting, hardware platform, or model. A professional adapter should record product version, license-relevant feature tier, scripting commands, model files, calculation logs, and exported results.[13] [17]

**Limitations and professional boundary.** The main limitation is legal and operational rather than numerical: the product requires a Bentley license and the EULA limits commercial hosting and fee-based service use. The second limitation is inspection: the proprietary implementation cannot be audited or modified like GPL/BSD-style source. The main professional advantage is domain specialization, vendor documentation, and geotechnical verification-case coverage. PLAXIS should be selected where a licensed geotechnical engineer and an authorized Bentley deployment are part of the operating model, not as a free backend for an unlicensed public service.[14] [15]

**C1–C80 relevance.** PLAXIS is directly relevant to **C06 Estructuras Profesionales** because it supports soil–structure and structural analysis in professional engineering workflows. It is conditionally relevant to **C62** where nonlinear structural/soil behavior and performance questions are in scope. Its groundwater/consolidation and soil-specific functions are highly relevant to the solver family, but no separately named geotechnical capability appears in the consulted C1–C80 list. The ARKI team must not imply that C06 or C62 is satisfied merely by connecting to PLAXIS; governance, engineering review, interoperability, and evidence capture remain separate requirements.

## Integration and evidence requirements for ARKI

A solver adapter should capture the exact solver name and version, operating-system and compiler/runtime identifiers, input files, mesh and material definitions, boundary and initial conditions, solver settings, random seeds where applicable, convergence logs, warnings, exit code, output files, and post-processing transformations. The adapter should never store only a chart or a prose conclusion as the computational record.

For all four candidates, the minimum regression fixture should include a small analytical or published benchmark, expected scalar/vector results with tolerances, a known-failure case, a convergence or mesh-sensitivity check, and a provenance manifest. For PLAXIS, add license tier and product entitlement metadata where the model uses tier-dependent functionality. For OpenSees and Code_Aster, add serial/parallel mode and dependency versions. For CalculiX, preserve the text deck and reference output file.

The professional boundary is explicit: a solver can calculate a numerical result, but it cannot by itself establish design adequacy, code compliance, safety, constructability, or professional authorization. C06 and C62 should therefore be implemented as a combined computational-plus-governance capability, not as a thin “run FEM” button.
