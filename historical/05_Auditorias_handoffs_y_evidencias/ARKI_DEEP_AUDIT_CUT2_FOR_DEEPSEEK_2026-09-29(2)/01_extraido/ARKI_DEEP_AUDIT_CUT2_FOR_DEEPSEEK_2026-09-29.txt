======================================================================
C. EVENT LOG REAL EN SICL-CORE
======================================================================

src/sicl/repository.py confirma SQLiteRepository.

Tabla events real:
- id INTEGER PRIMARY KEY AUTOINCREMENT
- timestamp TEXT
- project_id TEXT
- type TEXT
- payload TEXT
- actor TEXT
- source TEXT DEFAULT USER_COMMAND

Hay triggers:
- events_no_update
- events_no_delete

Por tanto events es append-only a nivel SQLite.

Métodos reales:
- add_event(event): inserta y commit
- _insert_event(event)
- add_events_atomic(events): batch all-or-zero
- events(project_id=None): lectura ordenada por id.

Event real en src/sicl/domain.py:
- id
- timestamp
- project_id
- type
- payload: dict
- actor
- source.

GET /v1/projects/{project_id}/history:
- verifica proyecto vía snapshot
- devuelve repo.events(project_id).

ESTO CORRIGE UNA PARTE DE LA PROPUESTA DE DEEPSEEK:
Sí existe infraestructura de event log append-only y puede reutilizarse.
Pero no existe actualmente un método semántico específico
insert_reasoning_execution_and_event ni una tabla reasoning_executions.

Por tanto NO debe decirse que "reasoning execution ya tiene persistencia canónica".
Existe un event log genérico capaz de registrar el evento; falta definir el contrato semántico del payload y su relación con snapshot/version.

======================================================================
D. PROBLEMA DE VERSIONADO DEL ENDPOINT PROPUESTO
======================================================================

DeepSeek propuso:
POST /v1/projects/{project_id}/reasoning-executions
request.observed_version = N
response.observed_version = N+1

Eso NO está todavía justificado por el repositorio.

Hecho observado:
repo.add_event() inserta evento y hace commit, pero por sí solo NO incrementa project.version.

En otros writes canónicos:
- preference crea entidad
- incrementa project.version
- persiste entidad + evento de forma coordinada.

Human review y decision pasan por CLI y la semántica de mutación del proyecto.

Por tanto un endpoint reasoning-executions no debe prometer N→N+1 sólo porque añade un Event.

DECISIÓN TÉCNICA A RESOLVER:
¿ReasoningExecution es:
A) evidencia/evento append-only que NO muta project snapshot/version;
o
B) entidad canónica proyectada en snapshot que SÍ debe versionar proyecto?

Mi recomendación técnica:
Para Brain/D6.2/D6.3, tratarlos como REASONING EVIDENCE / PROPOSAL HISTORY, no como arquitectura canónica.
El endpoint puede registrar un evento append-only y devolver el observed project version sin incrementarlo, salvo que se cree explícitamente una proyección de reasoning dentro del Project Snapshot.

No crear una tabla nueva sólo para forzar versión.

======================================================================
E. CONTRATO MÍNIMO RECOMENDADO PARA reasoning-executions
======================================================================

Antes de código, contrato sugerido:

POST /v1/projects/{project_id}/reasoning-executions

Payload:
{
  execution_id: stable fingerprint/id,
  kind: PROJECT_BRAIN | D6_2 | D6_3 | DEVELOPER_PROPOSAL,
  fingerprint: sha256,
  input_fingerprint: sha256 | null,
  payload: {...},
  epistemic_status: FACT | ASSUMPTION | HYPOTHESIS | UNKNOWN | CONFLICT,
  human_authority_ref: {...} | null,
  source_refs: [...],
  created_at: ISO timestamp
}

Persistencia mínima:
Event(
  type="REASONING_EXECUTION_RECORDED",
  payload=<validated envelope>,
  actor=<explicit actor>,
  source="ARKI_REASONING"
)

Invariantes:
- project debe existir.
- execution_id/fingerprint obligatorios.
- kind allowlist.
- payload no puede afirmar D-2 commit.
- D6.3 se registra HYPOTHESIS.
- DeveloperProposal se registra PROPOSAL/HYPOTHESIS.
- no promoción automática.
- no Human Decision implícita.
- event append-only.
- history permite replay/auditoría.
- observed_version refleja versión real del proyecto; no inventar +1.

FUTURO:
Si se necesita query eficiente por execution_id/kind, puede añadirse proyección/índice después. No es requisito para cerrar el primer E2E.

DeepSeek corrigió varias reglas inventadas, pero su output esperado todavía propone:

- SPACE local comercial rectángulo 7×7
- SPACE baño rectángulo 1.7×1.7
- WALL entre zonas

El encargo que él mismo define sólo proporciona:
- local area = 50
- baño area = 3
- site 10×10
- relación CONNECTED
- flow entrada→local→baño.

De 50 m² NO se deriva 7×7 (49 m²).
De 3 m² NO se deriva 1.7×1.7 (2.89 m²).
No hay evidencia para la posición exacta del muro.
CONNECTED no define por sí solo una puerta geométrica exacta.
"entrada" en flow no aporta ancho/posición de puerta.

Por tanto el microcaso propuesto TODAVÍA VIOLA la regla fail-closed si esos tamaños/elementos se tratan como output derivado.

CORRECCIÓN:
El microcaso debe aportar explícitamente geometría si el objetivo es probar transformación, o mantenerla UNKNOWN si el objetivo es probar reasoning.

Opción recomendada para MICROCASE-DEV-001:
INPUT EXPLÍCITO:
- site 10m×10m
- zona venta: rectangle 0,0, 5m×10m = 50m²
- zona baño: rectangle explícito 5m,0, 1.5m×2m = 3m²
- boundary entre ambas: explícito si se desea generar WALL
- opening location/width: UNKNOWN

Entonces Developer puede proponer SPACE geometry con provenance directa.
WALL sólo si boundary semantics y dimensiones son suficientes.
DOOR debe quedar UNKNOWN hasta que ubicación/ancho/host estén explícitos o derivados por una regla autorizada.

Esto prueba que ARKI NO inventa.
