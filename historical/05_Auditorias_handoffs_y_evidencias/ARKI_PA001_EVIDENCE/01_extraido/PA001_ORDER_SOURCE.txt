# ARKI — CAPACITACIÓN PREVIA 001
## PROGRAMA ARQUITECTÓNICO + RELACIONES ESPACIALES

AUTORIDAD:
Product Owner / Human Authority

EJECUTOR:
Manus

TIPO:
Capacitación + implementación controlada

OBJETIVO:
Dotar a ARKI de una capacidad básica y reutilizable para comprender qué necesita un espacio arquitectónico y qué relaciones funcionales debe mantener con otros espacios.

IMPORTANTE:

ESTA ORDEN NO IMPLEMENTA SINTAXIS ESPACIAL.

NO ejecutar, copiar, anticipar ni entrenar contra los exámenes A/B/C/D preparados por DeepSeek para la futura Capacidad 1 — Sintaxis Espacial.

No usar como fixtures de entrenamiento los casos de hospital/UCI/quirófanos, museo o colegio anunciados por DeepSeek para esos exámenes.

La finalidad es construir una capacidad complementaria y previa:

PROGRAMA REQUERIDO
        ↓
NECESIDADES DEL ESPACIO
        ↓
RELACIONES ESPACIALES ESPERADAS
        ↓
PROYECTO OBSERVADO
        ↓
COMPARACIÓN
        ↓
DÉFICITS / CONFLICTOS / UNKNOWN

No memorizar soluciones.

No hardcodear respuestas arquitectónicas.

--------------------------------------------------
1. PRINCIPIO
--------------------------------------------------

Actualmente un espacio no debe ser entendido únicamente como:

nombre + área + geometría.

ARKI debe empezar a comprenderlo como una entidad funcional:

ESPACIO
→ ACTIVIDAD
→ USUARIO
→ CAPACIDAD
→ MOBILIARIO/EQUIPO
→ DIMENSIONES
→ ACCESOS
→ ADYACENCIAS
→ PROXIMIDADES
→ SEPARACIONES
→ PRIVACIDAD
→ FLUJOS
→ RELACIONES VISUALES
→ ILUMINACIÓN
→ VENTILACIÓN
→ ACÚSTICA
→ ACCESIBILIDAD
→ SEGURIDAD
→ SERVICIOS
→ RESTRICCIONES
→ EVIDENCIA
→ UNKNOWN

Esta capacitación NO pretende resolver profesionalmente todas esas dimensiones.

Pretende crear el modelo arquitectónico necesario para representarlas, razonarlas y detectar cuándo existe o falta evidencia.

--------------------------------------------------
2. REGLA EPISTÉMICA
--------------------------------------------------

No convertir conocimiento incompleto en hecho.

Distinguir como mínimo:

REQUIRED
PREFERRED
PROHIBITED
OBSERVED
INFERRED
SATISFIED
VIOLATED
UNKNOWN
NOT_APPLICABLE
PROFESSIONAL_VALIDATION_REQUIRED

Un requisito no demostrado NO puede convertirse automáticamente en incumplimiento.

Ausencia de evidencia:

≠ FALSE
≠ VIOLATED

Debe poder permanecer:

UNKNOWN

--------------------------------------------------
7. PROGRAMA ESPERADO VS PROYECTO OBSERVADO
--------------------------------------------------

Crear una capacidad que permita comparar:

EXPECTED PROGRAM
vs
OBSERVED PROJECT STATE

Ejemplo conceptual:

Programa:
A debe estar próximo a B.

Proyecto:
A y B no presentan evidencia suficiente para determinar proximidad.

Resultado:

UNKNOWN

No:

VIOLATED

Otro ejemplo:

Programa:
A debe tener acceso directo a B.

Proyecto:
la relación observada demuestra que A solamente conecta con B pasando por C.

Resultado:

VIOLATED

con evidencia trazable.

8. RESULTADO DE EVALUACIÓN
--------------------------------------------------

Definir un resultado similar conceptualmente a:

ProgramEvaluationResult

que pueda contener:

satisfiedRelations

notApplicableRelations

provenance

No crear un único “architectureScore”.

No reducir calidad arquitectónica a un número.

Puede haber métricas parciales, pero deben conservar significado.

--------------------------------------------------
9. CONFLICTOS
--------------------------------------------------

ARKI debe detectar contradicciones explícitas.

Ejemplo:

A MUST_BE_ADJACENT_TO B

y simultáneamente:

A MUST_BE_SEPARATED_FROM B

Si ambas tienen igual aplicabilidad:

CONFLICT

No elegir silenciosamente una.

Reportar:

CONFLICT_DETECTED

y conservar ambas reglas con su procedencia.

--------------------------------------------------
13. TESTS BÁSICOS
--------------------------------------------------

Crear pruebas ejecutables.

Como mínimo:

PA-T01
Dos espacios con relación ADJACENT_TO demostrada.
Resultado:
SATISFIED.

PA-T02
ADJACENT_TO requerido pero evidencia demuestra separación.
Resultado:
VIOLATED.

PA-T03
ADJACENT_TO requerido pero proyecto no contiene evidencia suficiente.
Resultado:
UNKNOWN.

PA-T04
Relación PREFERRED incumplida.
No debe tratarse igual que MANDATORY.

PA-T05
Relaciones contradictorias.
Resultado:
CONFLICT_DETECTED.

PA-T06
Mismo programa evaluado dos veces.
Resultado determinista.

PA-T07
Cambio de nombres/IDs preservando semántica.
El resultado funcional no debe cambiar.

PA-T08
Espacio inexistente en Project State.
No crash.
Reportar missing/UNKNOWN según corresponda.

PA-T09
Regla NOT_APPLICABLE.
No contabilizar como violación.

PA-T10
Dos proyectos diferentes.
No contaminación cruzada.

--------------------------------------------------
14. ADVERSARIALES
--------------------------------------------------

Crear casos para intentar romper la capacidad.

Como mínimo:

PA-A01
Relación circular:
A depende de B,
B depende de C,
C depende de A.

No crash.

PA-A02
Reglas duplicadas.

Deduplicar o conservar conscientemente según provenance.

PA-A03
Dos fuentes contradictorias.

No elegir silenciosamente.

PA-A04
Requirement sin provenance.

Debe conservar UNKNOWN_SOURCE o equivalente.

PA-A05
Espacio sin geometría.

Debe poder seguir existiendo como requisito programático.

PA-A06
Espacio observado sin requisito programático.

No eliminarlo.

PA-A07
Programa con 500 espacios y múltiples relaciones.

Prueba razonable de rendimiento.

PA-A08
Input malformado.

Fail closed / error explícito.

15. TESTS METAMÓRFICOS
--------------------------------------------------

PA-M01

PA-M02

PA-M03

PA-M04

PA-M05

--------------------------------------------------
16. TEST THE TEST
--------------------------------------------------

No basta con que los tests estén verdes.

Introducir temporalmente mutaciones controladas para comprobar que las pruebas fallan.

Como mínimo intentar:

- UNKNOWN → SATISFIED
- UNKNOWN → VIOLATED
- ignorar prioridad
- ignorar contradicciones
- considerar PREFERENCE como MANDATORY
- eliminar provenance
- compartir estado entre proyectos

Registrar qué tests matan cada mutación.

Después restaurar código correcto.

--------------------------------------------------
22. PRINCIPIO FINAL
--------------------------------------------------

El objetivo NO es que ARKI memorice:

“cocina debe estar junto a comedor”.

El objetivo es que ARKI aprenda:

“existe una relación funcional requerida entre dos espacios; conozco su tipo, prioridad, procedencia y aplicabilidad; puedo comparar esa relación con el proyecto observado; puedo determinar si está satisfecha, violada o permanece desconocida; y puedo explicar por qué.”

Eso es la capacidad que queremos construir.

PROGRAMA ≠ GEOMETRÍA

RELACIÓN ESPERADA ≠ RELACIÓN OBSERVADA

AUSENCIA DE EVIDENCIA ≠ INCUMPLIMIENTO

PREFERENCIA ≠ NORMA

HEURÍSTICA ≠ VERDAD UNIVERSAL

TEST VERDE ≠ COMPETENCIA PROFESIONAL

IMPLEMENTACIÓN ≠ VERIFICACIÓN INDEPENDIENTE

HUMAN AUTHORITY permanece vigente.

Procede.
